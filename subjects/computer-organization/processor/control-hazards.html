從管線化接著往下：分支讓 IF 不知道下一條要抓誰

Pipelining 管線化那一頁已經介紹過三種危障，也提過最簡單的處理：遇到分支就 stall 到結果出來。這一頁專門處理分支。先用三句話複習：

  • IF 每個週期都要抓一條新指令，但遇到 beq、bne 時，要比較完兩個暫存器才知道下一條是 PC + 4 還是分支目標，這叫 Control Hazard（控制危障，又叫 branch hazard）。
  • 分支成立、真的跳到目標，叫 Taken（跳）；不成立、照順序往下走，叫 Not Taken（不跳）。目標位址 = PC + 4 + 位移 × 4，計算方式在 MIPS Instruction Formats MIPS 指令格式講過，這裡不重複。
  • 因為分支而白白浪費的週期數，叫 Branch Penalty（分支損失）。

考題幾乎都在問同一件事的不同面向：分支要等多久才知道結果、這段時間 IF 做了什麼、猜錯要丟掉幾條、平均起來讓 CPI 多了多少。這一頁依序講：

  1. 分支在 ID、EX、MEM 決定時，penalty 各是多少，猜錯要 Flush（清除）幾條指令。
  2. 四種不需要記錄歷史的做法：stall、predict-not-taken、predict-taken、delayed branch，以及 delay slot 的三種填法。
  3. 分支造成的 CPI 損失：分支比例 × 付出代價的比例 × penalty。
  4. 動態預測：1-bit、2-bit 計數器（兩種狀態圖版本），以及迴圈、給定序列時的正確率怎麼算。
  5. BTB、correlating predictor、tournament predictor 等進一步的做法。

例子都用 MIPS 五階段管線（IF、ID、EX、MEM、WB），階段編號 IF = 1、ID = 2、EX = 3、MEM = 4。分支在哪一級決定每一題的設定都不同，題目一定會寫，先找出這個條件再開始算。

分支在哪一級決定：penalty 與 flush 幾條

設分支在第 1 個週期 IF，在第 k 級（IF = 1）結束時才知道結果。從第 2 個週期到第 k 個週期，IF 每個週期都必須做點什麼：要嘛不抓（stall），要嘛先抓一條「猜的」。不管哪一種，這 k − 1 個週期抓的東西都可能是白做的：

penalty（最多損失的週期數）= 決定的階段編號 − 1
ID 決定 → 1　　EX 決定 → 2　　MEM 決定 → 3
分支在哪一級結束時決定決定前 IF 已經用掉的週期一律 stall 時每個分支停猜錯時要 flush 的指令
ID（比較器、目標加法器搬到 ID）第 2 週期11 條（IF/ID 裡那條）
EX（ALU 比較）第 2、3 週期22 條（IF/ID、ID/EX 裡的）
MEM（最原始的 datapath：在 MEM 才更新 PC）第 2～4 週期33 條（IF、ID、EX 三級裡的）

為什麼要把分支提早到 ID

決定得越早，penalty 越小。把分支搬到 ID 要加兩樣硬體：一個 相等比較器（beq 只需要比是否相等，用 XOR 再 OR 起來就好，比完整的 ALU 快很多，所以塞得進 ID）、一個 計算目標的加法器。另外還要一個 IF.Flush 訊號：猜錯時把 IF/ID 管線暫存器清成 nop，這就是 flush。

代價是 beq 在 ID 就要用到暫存器的值，比一般指令早一個週期，資料危障變多：前一條是 ALU 指令要停 1 個週期，前一條是 lw 要停 2 個週期。這部分在 Data Hazards and Forwarding 資料危障與轉送已經詳細講過，算題目時記得兩種 stall 要分開加。

管線越深，penalty 越大

為了提高時脈，現代處理器把管線切成十幾級，分支的比較可能到第 10 級以後才完成，猜錯一次就要丟掉十幾條指令。所以時脈越高的處理器越需要準確的分支預測。反過來，如果某個設計為了提早決定分支而拉長了時脈週期，就要把「CPI 變小」和「每個週期變長」放在一起比，不能只看 penalty（例題見練習題）。

看程式碼：branchPenalty() 決定階段與 penalty
branchPenalty()：決定前已經多抓了 resolve − 1 條
int branchPenalty(int resolve) {
  return resolve - 1;
}

完成週期題怎麼算

有些考題給一段程式和「實際執行順序」，要你寫出每條指令在哪個週期完成。分支這部分的規則只有兩條：

  • 猜對：下一條照常在分支的下一個週期 IF，沒有損失（猜 taken 要能在 IF 就拿到目標，否則還是要等目標算出來）。
  • 猜錯：正確的下一條在「分支決定的那個週期的下一個週期」才 IF。分支在 EX 決定、EX 在週期 6，正確的指令就在週期 7 IF。

再加上資料危障的 stall（沒有 forwarding 要等 WB；分支在 ID 比較要多等），一條一條往下排就好。

四種靜態做法：stall、猜不跳、猜跳、delayed branch

「靜態」指做法在執行前就固定，硬體不記錄每個分支過去的行為。設 penalty = p（分支決定的階段編號 − 1）：

做法決定之前 IF 做什麼實際 taken 時損失實際 not taken 時損失
一律 stall什麼都不抓pp
Predict-Not-Taken（預測不跳）照常抓 PC + 4p（flush 掉）0
Predict-Taken（預測跳），IF 就拿得到目標從目標抓0p（flush 掉）
Delayed Branch（延遲分支），1 個 slot抓分支後面那一條，一定執行p − 1p − 1

Predict-not-taken：最便宜的猜法

IF 本來就會抓 PC + 4，所以「猜不跳」完全不用額外硬體，只需要猜錯時能 flush：把已經進入管線的錯誤指令的控制訊號清成 0，讓它們變成 bubble。被 flush 的指令還沒走到 MEM、WB，不會寫記憶體或暫存器，所以猜錯只浪費時間，不會改變程式的結果。換句話說，stall、predict-not-taken、各種動態預測，只要硬體正確處理，程式看得到的暫存器與記憶體內容完全一樣，差別只在花了幾個週期。也因此，把「一律 stall」換成任何靜態預測，CPI 只會變小或一樣，不會變大：猜對省下 p 個週期，猜錯也只是和 stall 一樣付出 p。

Predict-taken：要先知道目標

猜跳的前提是 IF 下一個週期就能從目標抓指令。但目標位址要等 ID 解碼、加法器算出來；在標準的五階段管線裡，就算猜 taken 而且猜對，也要等到 ID 才知道目標，仍損失 1 個週期。所以 predict-taken 通常搭配 BTB（後面介紹）：在 IF 就用 PC 查出目標。題目寫「when a branch is predicted taken, the target address is also predicted」就是這個意思，猜對 taken 的損失是 0。

依方向猜：向後跳猜 taken

迴圈尾端的分支是往回跳（目標位址比較小），大部分時間都是 taken；if 判斷常是往前跳，比較常不跳。所以有一種靜態規則是 BTFN（Backward Taken, Forward Not taken）：往回跳猜 taken、往前跳猜 not taken，編譯器也可以在指令裡加提示位元。

考題常問「一個 for 迴圈用 always-taken 和 always-not-taken 哪個準」。答案取決於分支怎麼編譯：如果判斷放在迴圈尾端、用向後分支跳回去，n 圈的迴圈這個分支執行 n 次，前 n − 1 次 taken，always-taken 準確率 (n − 1)/n；如果判斷放在開頭、條件不成立就往前跳出去，這個分支執行 n + 1 次，前 n 次 not taken，反而是 always-not-taken 比較準。題目沒有給組合語言時，作答要寫出假設。

看程式碼：fetchTrace() 四種做法下 IF 每個週期抓什麼
Strategy 與 Fetch 結構
typedef enum { STALL, PREDICT_NT, PREDICT_T, DELAYED } Strategy;

typedef struct {
  char name[12];   /* 抓進來的是哪一條：beq、i+1、i+2…（循序）、t1、t2…（目標）、slot、bubble */
  int cycle;       /* 在第幾個週期 IF */
  int flushed;     /* 1：猜錯，被清掉（變成 bubble） */
} Fetch;
fetchTrace()：回傳損失的週期數（bubble + flush）
int fetchTrace(Strategy st, int resolve, int taken, Fetch *out, int n) {
  int lost = 0, seq = 1, tgt = 1;
  snprintf(out[0].name, sizeof out[0].name, "beq");
  out[0].cycle = 1;
  out[0].flushed = 0;
  for (int c = 2; c <= n; c++) {
    Fetch *f = &out[c - 1];
    f->cycle = c;
    f->flushed = 0;
    if (c > resolve) {                              /* 結果已知：照實際方向抓 */
      if (taken) snprintf(f->name, sizeof f->name, "t%d", tgt++);
      else snprintf(f->name, sizeof f->name, "i+%d", seq++);
    } else if (st == DELAYED && c == 2) {           /* delay slot：不管跳不跳都執行 */
      snprintf(f->name, sizeof f->name, "slot");
      seq = 2;                                      /* slot 就是原本的 i+1 */
    } else if (st == STALL || st == DELAYED) {      /* 還不知道：什麼都不抓 */
      snprintf(f->name, sizeof f->name, "bubble");
      lost++;
    } else if (st == PREDICT_NT) {                  /* 猜不跳：照常抓 PC + 4 */
      snprintf(f->name, sizeof f->name, "i+%d", seq++);
      if (taken) { f->flushed = 1; lost++; }
    } else {                                        /* 猜跳：BTB 在 IF 就給出目標 */
      snprintf(f->name, sizeof f->name, "t%d", tgt++);
      if (!taken) { f->flushed = 1; lost++; }
    }
  }
  return lost;
}

Delayed Branch：delay slot 的三種填法

Delayed branch 是直接改 ISA 的規定：分支後面那一條指令不管跳不跳都會執行，這個位置叫 Branch Delay Slot（分支延遲槽）。MIPS 的分支就有 1 個 delay slot。硬體因此在決定之前永遠有一條「一定要做」的指令可以抓；分支在 ID 決定時（penalty = 1），只要 slot 裡放的是有用的指令，分支就完全沒有損失。

重點是誰負責把有用的指令放進 slot：是編譯器（或寫組合語言的人）。硬體只是照規定執行，所以 delayed branch 是靠軟體排程的技巧，需要編譯器配合；動態預測、forwarding 則完全是硬體的事，程式不用改。找不到合適的指令時，只能放 nop，這時就等於 stall 1 個週期。

來源什麼時候有用條件適合
(a) from before（分支之前）一定有用（本來就要做）搬下去後不影響分支判斷：不能寫分支要比較的暫存器，也不能是分支條件所依賴的指令鏈的一部分首選，找得到就用它
(b) from target（目標）只有 taken 時有用not taken 時白做也不能出錯：它寫的暫存器在不跳的那條路上不能先被讀；要用「複製」的，分支改跳到目標的下一條大多數會 taken 的分支，例如迴圈
(c) from fall-through（不跳的路）只有 not taken 時有用taken 時白做也不能出錯：它寫的暫存器在目標那條路上不能先被讀大多數不跳的分支

「白做也不能出錯」的意思是：slot 裡的指令不能做任何在那條路上會被看見的事。寫一個之後會先被覆寫、不會被讀到的暫存器沒關係；寫記憶體（sw）或可能引發例外的指令就很危險，通常不搬。

為什麼現代處理器不用了

  • 只蓋得住 1 個週期：分支在 ID 決定時剛好；但管線一深、penalty 變成 10 個週期以上，就要十幾個 slot，編譯器根本找不到那麼多獨立的指令。
  • 一次發好幾條指令的處理器（multiple issue，在 Instruction-Level Parallelism 指令層級平行（籌備中）介紹），一個週期就要填好幾個 slot，問題更嚴重。
  • 寫進 ISA 就改不掉：delay slot 是指令集規格的一部分，之後的處理器就算管線完全不同，也得繼續支援這個規定。這是它和管線實作綁太緊的缺點，所以「delayed branch 對長管線很有用」是錯的。

考題問 delayed branch 算不算「hardware technique」時要小心：它的確要硬體照規定執行，但填 slot 這件事是編譯器做的，所以大多數教材把它歸為需要編譯器配合的技巧。

分支造成的 CPI 損失

把每個分支的損失平均到每一條指令（CPI 的定義與 CPU 時間的公式見 CPU Time and CPI CPU 時間與 CPI；資料危障和分支一起算的寫法見管線化的「把 stall 算進效能」）：

CPI = 基本 CPI + 分支比例 × 付出代價的比例 × penalty

付出代價的比例：
  一律 stall          → 1（每個分支都付）
  predict-not-taken   → taken 的比例
  predict-taken（BTB）→ not taken 的比例
  動態預測            → 預測錯誤率 = 1 − 正確率

最常見的陷阱是題目給「正確率」：正確率 20% 代表 80% 的分支猜錯，要乘的是 0.8，不是 0.2。

例子

15% 的指令是分支，其中 70% taken；基本 CPI = 1，分支在 MEM 決定（p = 3）：

做法計算CPI意義
一律 stall1 + 0.15 × 1 × 31.45比理想慢 45%，將近一半的時間在等分支
predict-not-taken1 + 0.15 × 0.7 × 31.315taken 的分支比較多，猜不跳只省了 30% 的損失
動態預測，正確率 92%1 + 0.15 × 0.08 × 31.036損失剩 3.6%，只有 stall 的 8%
動態預測 + 分支搬到 ID（p = 1）1 + 0.15 × 0.08 × 11.012再降到 1.2%，前提是時脈沒有變慢

比較兩個設計時，CPI 只是一半：執行時間 = 指令數 × CPI × 週期時間。把分支提早決定可能讓 ID 變長、拖慢整個時脈；這時要把兩邊的「CPI × 週期時間」算出來比，才知道哪個比較快。

看程式碼：branchCPI() 加上分支損失的 CPI
branchCPI()：基本 CPI + 分支比例 × 付出代價的比例 × penalty
double branchCPI(double baseCPI, double branchFrac, double missRate, int penalty) {
  return baseCPI + branchFrac * missRate * penalty;   /* 每條指令平均多出的週期 */
}

動態預測：1-bit 與 2-bit 計數器

靜態做法對每個分支都用同一套規則，但每個分支的習性不一樣：迴圈的分支幾乎總是 taken，檢查錯誤的分支幾乎總是 not taken。Dynamic Branch Prediction（動態分支預測）在執行時記錄每個分支最近的行為，用來猜下一次。

Branch History Table

最簡單的硬體是 Branch Prediction Buffer（分支預測緩衝區，又叫 Branch History Table, BHT）：一塊很小的記憶體，用分支指令 PC 的低位元當索引（最低 2 位元一定是 00，所以從第 2 位元往上取），每一格存 1 或 2 個位元的預測。例如 1024 格的 BHT 用 PC 的第 2～11 位元選格子。

  • 沒有 tag：格子裡不記錄「這是哪個分支的歷史」，所以低位元相同的兩個分支會共用同一格，互相干擾（aliasing），拿到別的分支的歷史而猜錯。
  • 猜錯只影響效能，不影響正確性：反正猜錯會 flush，所以 BHT 可以做得又小又簡單，不用檢查 tag。

1-bit：記住上一次

每格 1 個位元，記錄這個分支上一次是 taken 還是 not taken，下次就猜一樣的。問題出在迴圈：內圈跑 n 次的分支，結果是 T T … T N，接著下次進入迴圈又是 T T … T N。1-bit 在最後一次 N 猜錯（它記著 T），然後記成 N；下次進入迴圈的第一次 T 又猜錯。每次離開迴圈都要錯 2 次，即使這個分支 n − 1 次都是 taken。

2-bit 飽和計數器

改成每格 2 個位元，當成 0～3 的計數器：taken 加 1、not taken 減 1，到 3 或 0 就停住（飽和）；值 ≥ 2 預測 taken。四個狀態寫成二進位：

狀態名稱預測遇到 taken遇到 not taken
11強 taken（strongly taken）T停在 11→ 10
10弱 taken（weakly taken）T→ 11→ 01
01弱 not takenN→ 10→ 00
00強 not takenN→ 01停在 00

這樣一次例外（例如迴圈最後一次的 N）只會讓 11 退到 10，下次還是猜 T。所以 2-bit 的特性是：在強狀態時，要連續猜錯兩次才會改變預測；在弱狀態時錯一次就會換邊。內圈 n 次的迴圈，2-bit 每次離開只錯 1 次。

注意 2-bit 計數器只看這一條分支自己的歷史。它比 1-bit 好，是因為多了「遲滯」（要錯兩次才改），不是因為用了其他分支的資訊；那是後面 correlating predictor 的事。

同一個狀態圖，題目的畫法可能不一樣

考題附的狀態圖常常排成 2 × 2 的方形（左上強 taken、右上弱 taken、右下弱 not taken、左下強 not taken），而且狀態的編碼不一定一樣：有的題目用 11 代表強 taken，有的反過來用 00、01 代表預測 taken，10、11 代表預測 not taken。起始狀態也每題不同（有的從強 taken 開始，有的從強 not taken 開始）。作答前先把題目的圖轉成「哪幾個狀態預測 T、taken 往哪走、not taken 往哪走、從哪裡開始」，不要背編碼。

另一種 2-bit：跳躍版

除了飽和計數器，還有一種常見的 2-bit 狀態圖：在弱狀態又猜錯時，直接跳到另一邊的強狀態，而不是走到另一邊的弱狀態。強狀態的行為和飽和計數器一樣（錯一次退到弱狀態）。

兩種版本在「強狀態錯一次不改預測」這點相同，所以迴圈的計算結果通常一樣；但在 T、N 交錯的序列上會不同。例如從 00 開始，序列 T T N T T T N T：飽和版猜對 3 次，跳躍版猜對 4 次（第 2 次 T 讓跳躍版直接到 11，後面比較穩）。換一個序列可能反過來，沒有哪一版永遠比較好。考古題附圖的都是飽和計數器，題目沒畫圖時就用飽和計數器，並寫出假設。

看程式碼：predictTaken() 與 nextState()（1-bit／2-bit 飽和／跳躍版）
Kind 與狀態的意義
typedef enum { ONE_BIT, TWO_BIT_SAT, TWO_BIT_JUMP } Kind;
/* 狀態：1-bit 用 1 = 上次 taken、0 = 上次 not taken；
 * 2-bit 用 3 = 強 taken、2 = 弱 taken、1 = 弱 not taken、0 = 強 not taken */
predictTaken()：1-bit 看上一次，2-bit 看 ≥ 2
int predictTaken(Kind k, int s) {
  if (k == ONE_BIT) return s == 1;
  return s >= 2;                                    /* 2 和 3 預測 taken */
}
nextState()：依實際結果更新狀態
int nextState(Kind k, int s, int taken) {
  if (k == ONE_BIT) return taken;                   /* 只記住上一次的結果 */
  if (k == TWO_BIT_JUMP) {                          /* 跳躍版：弱狀態猜錯直接跳到另一邊的強狀態 */
    if (taken && s == 1) return 3;
    if (!taken && s == 2) return 0;
  }
  if (taken) return s < 3 ? s + 1 : 3;              /* 飽和計數器：往上加，最多到 3 */
  return s > 0 ? s - 1 : 0;                         /* 往下減，最少到 0 */
}

迴圈與序列的預測正確率怎麼算

不管題目怎麼包裝，步驟都一樣：

  1. 寫出這個分支每一次的實際結果（T/N 序列）。迴圈尾端的向後分支，內圈 n 次就是「n − 1 個 T、1 個 N」，外圈每跑一次就重複一輪。
  2. 從題目給的初始狀態開始，每一次：用目前狀態預測 → 和實際比 → 依實際結果轉到下一個狀態。
  3. 數猜對幾次，除以總次數。

迴圈的公式

內圈 n 次、整段重複 m 輪，1-bit 初始為 T、2-bit 初始為 11 或 10：

預測器第一輪錯幾次之後每輪錯幾次正確率n = 4、m = 3
always taken11(n − 1)/n9/12 = 75%
1-bit1（最後的 N）2（第一次的 T + 最後的 N）[(n − 1) + (m − 1)(n − 2)] / mn7/12 ≈ 58%
2-bit11(n − 1)/n9/12 = 75%

三個容易算錯的地方：

  • 初始狀態：1-bit 初始 N（或 2-bit 從 01、00 開始）時，第一輪前面還會多錯幾次，公式要調整，最保險是照步驟逐次追。
  • 外層迴圈只跑幾次時：外層分支的序列很短（例如 T T N），1-bit 和 2-bit 都只錯最後一次，正確率一樣，不是 2-bit 一定比較高。2-bit 的優勢要在「離開之後又會再進來」的分支上才看得出來。
  • 「重複很多次」問的是穩態：一個模式重複 r 次，前幾輪的狀態還在變，正確率會和之後不同。跑個兩三輪，如果某一輪開始時的狀態和上一輪開始時一樣，之後每一輪就完全重複，長期的正確率就是那一輪的正確率，不是前幾輪的平均。
看程式碼：runPredictor() 與 loopOutcomes()
runPredictor()：逐次預測、比對、更新狀態
int runPredictor(Kind k, int *state, const int *outcome, int n, int verbose) {
  int correct = 0;
  for (int i = 0; i < n; i++) {
    int p = predictTaken(k, *state);
    if (p == outcome[i]) correct++;
    if (verbose)
      printf("  #%-2d 狀態 %d 預測 %c 實際 %c %s\n", i + 1, *state,
             p ? 'T' : 'N', outcome[i] ? 'T' : 'N', p == outcome[i] ? "對" : "錯");
    *state = nextState(k, *state, outcome[i]);
  }
  return correct;
}
loopOutcomes()：產生迴圈分支的 T/N 序列
int loopOutcomes(int inner, int outer, int *outcome) {
  int n = 0;
  for (int r = 0; r < outer; r++)
    for (int i = 0; i < inner; i++) outcome[n++] = (i < inner - 1);
  return n;
}

BTB 與更進一步的預測器

Branch Target Buffer：在 IF 就知道目標

BHT 只回答「跳不跳」，不知道跳去哪裡；目標要等 ID 算出來，猜 taken 至少還是損失 1 個週期。Branch Target Buffer（分支目標緩衝區，BTB）是一個存「分支的 PC → 上次跳去的目標」的小 cache，在 IF 階段和抓指令同時用 PC 查：查到了而且預測 taken，下一個週期就直接從目標抓，猜對時完全沒有損失。

BHT（branch prediction buffer）BTB
存什麼1 或 2 個預測位元目標位址（常附預測位元）
有沒有 tag沒有，aliasing 只會讓預測變差有，用錯別的分支的目標會跳到莫名其妙的地方，所以要確認
什麼時候查ID（已經知道是分支）或 IFIF（還沒解碼就要決定下一個 PC）
猜 taken 猜對的損失還要等目標算出來0

Correlating predictor：看其他分支

有些分支的結果和前面其他分支有關。例如先判斷 if (x == 0)、再判斷 if (x >= 0)：前一個成立時後一個一定成立。2-bit 計數器只看自己，抓不到這種關係。Correlating Predictor（相關預測器）用一個 global history 暫存器記住最近幾個分支（不管是哪一條）的結果，和這條分支自己的 PC 一起選計數器：同一條分支，在「前面分支走法不同」的情況下用不同的計數器。這種寫法叫 (m, n) 預測器：用最近 m 個分支的結果，從 2m 個 n-bit 計數器裡選一個。

Tournament predictor：讓兩種預測器比賽

有的分支適合看自己的歷史（local），有的適合看全域歷史（global）。Tournament Predictor（競賽預測器）同時做兩種預測，再用每個分支一個 2-bit 的選擇器記錄「最近誰比較準」，就聽誰的。選擇器的更新方式和 2-bit 計數器一樣，要連續贏兩次才換人。

Indirect branch 與 return

jr $t0 這種目標放在暫存器裡的 Indirect Branch（間接分支）（switch 的跳躍表、函式指標、虛擬函式），每次的目標都可能不同，BTB 只記得上一次的目標，所以比條件分支更難預測。函式返回（jr $ra）有固定的規律：回到最近一次呼叫的下一條，所以處理器用一個小堆疊（return address stack）專門記返回位址。

乾脆不要分支：條件選擇

很短的 if-else 可以改寫成沒有分支的程式：兩邊的值都算，再用一條條件選擇指令依條件挑一個寫入，例如 ARMv8 的 CSEL、MIPS 的 movn / movz。分支少了，就沒有猜錯的代價；缺點是兩邊都要算，只適合很短的分支。另外，迴圈展開（loop unrolling）可以減少迴圈分支執行的次數，在 Instruction-Level Parallelism 指令層級平行（籌備中）介紹。

最後補充：猜錯時「flush 掉錯誤路徑、從正確的位址重新抓」這套機制，處理器遇到例外時也會用到，在 Exceptions 例外處理（籌備中）介紹。

易錯點

  • 分支提早到 ID 決定，每個分支仍要停 2 個週期 → ID 結束就知道結果，只有 IF 多抓的那 1 條，penalty 是 1 例題
  • 分支在 MEM 決定，penalty 是 4 → 決定前 IF 只多抓了 IF、ID、EX 三級裡的 3 條，penalty = 4 − 1 = 3 例題
  • 題目給「預測正確率 20%」就乘 0.2 → 付出代價的是猜錯的 80%，要乘 0.8 例題
  • 加了靜態預測，猜錯時要 flush，CPI 可能比一律 stall 更大 → 猜錯的代價和 stall 一樣是 p，猜對還省下 p，CPI 只會變小或一樣 例題
  • 猜錯時錯誤路徑上的指令已經執行了，結果可能不同 → 被 flush 的指令還沒走到 MEM、WB，不會寫回任何東西，架構結果完全相同 例題
  • 1-bit 預測器在迴圈裡每次離開只錯 1 次 → 離開那次錯，下次進入的第一次又錯，每輪錯 2 次 例題
  • 2-bit 計數器猜錯一次就改變預測 → 在強狀態要連錯兩次才換邊；在弱狀態錯一次就換 例題
  • 2-bit 的正確率一定比 1-bit 高 → 外層只跑幾次的分支（T T N）兩者一樣；有些交錯的序列 2-bit 甚至不比較好 例題
  • 2-bit 狀態一律是 11 = 強 taken → 編碼、起始狀態、甚至狀態圖版本都依題目，先讀懂圖再追 例題 例題
