Deadlock Avoidance and Banker's Algorithm 死結避免與銀行家演算法先試算再發資源，只讓系統停在安全狀態

Ch5 Deadlocks 難度 Banker's algorithm safe state safe sequence claim edge

為什麼要「避免」死結

一組行程裡，每個行程都在等「另一個行程手上的資源」，而大家都不放手，結果誰都跑不下去，這就是 Deadlock（死結）。死結要同時滿足四個條件才會發生：Mutual Exclusion（互斥）、Hold and Wait（持有並等待）、No Preemption（不可搶奪）、Circular Wait（循環等待）。這四個條件和怎麼一條一條破壞它們，會在「Deadlock Characterization and Prevention 死結的條件與預防」那一頁詳細講（籌備中），這裡只需要記得：四個條件缺一個，死結就不會發生。

作業系統面對死結，大致有四種態度：

策略做法什麼時候出手代價
Deadlock Prevention（死結預防）設計規則，讓四個條件中至少一個永遠不成立（例如規定資源要照編號由小到大申請，就不可能循環等待）寫程式、設計系統的時候規則很死板，資源使用率低，可能飢餓
Deadlock Avoidance（死結避免）四個條件都允許，但每次有人申請資源時先試算：給了之後系統還安不安全，不安全就不給每一次資源請求要事先知道每個行程的最大需求；每次請求都要跑演算法
Deadlock Detection and Recovery（死結偵測與復原）平常想給就給，定期（或 CPU 使用率突然下降時）檢查有沒有死結，有就砍行程或搶資源死結發生之後偵測要花時間；復原時被砍掉的行程要重做
忽略（鴕鳥演算法）假設死結很少發生，真的發生就讓使用者或管理員重開不處理一般桌上型作業系統多半這樣做，成本最低

這一頁的主角是「避免」。它和「預防」最大的差別是：預防是從結構上讓死結不可能；避免則不限制行程怎麼要資源，而是每次發資源之前都先看一下未來，只要有任何可能走進死結的風險就先擋下來。這就像銀行放款：銀行手上的現金有限，它不會因為「現在金庫裡錢夠」就借，而是要確定借了之後，所有客戶最壞情況下要提的錢都還有辦法依序滿足。這也是這個演算法叫 Banker's Algorithm（銀行家演算法）的原因。

一句話記：預防是「改規則讓死結不可能」，避免是「每次發資源前先試算，只停在安全的狀態」，偵測是「先發再說，出事再救」。

Safe State 與 Unsafe State

避免的核心是一個定義：系統處於 Safe State（安全狀態），意思是存在某個行程的排列 <Pa, Pb, …>，讓每個行程依照這個順序都能拿到它最多可能要的資源、跑完、再把資源還回來。這個排列叫 Safe Sequence（安全序列）。更精確地說，序列中第 k 個行程還需要的資源，必須 ≤「目前剩下的資源」加上「排在它前面的行程全部歸還的資源」。

找不到任何安全序列的狀態叫 Unsafe State（不安全狀態）。這裡最容易誤會的一點是：unsafe 不等於已經死結。

例子：unsafe 但還沒死結

只有一種資源、總共 10 個。三個行程宣告的最大需求和目前已拿到的數量如下，剩下 Available = 10 − 4 − 2 − 2 = 2 個。

行程MaxAllocationNeed
P0844
P1321
P2725

這是 safe：先給 P1 它要的 1 個，它跑完歸還 3 個，手上變 4 個；再滿足 P0 的 4 個，P0 歸還 8 個；最後 P2 要 5 個也沒問題。安全序列是 <P1, P0, P2>。

如果這時 P2 再要 1 個、系統也給了，剩下 1 個：P1 要 1 個還是能跑完，歸還後剩 3 個，但 P0 還要 4 個、P2 還要 4 個，都不夠，找不到安全序列，進入 unsafe。可是現在還沒有死結：Max 只是「最多可能要」，如果 P0 其實只再要 2 個就做完並歸還，大家都能順利結束。unsafe 的意思是「系統已經沒辦法保證」，最壞情況（每個人都真的要到 Max）一出現就會死結。銀行家演算法保守地把這種風險擋掉，所以剛才 P2 那 1 個的請求，會被要求先等一等。

三者的關係：safe ⇒ 不會死結；deadlock ⇒ unsafe；但 unsafe 不一定 deadlock。寫成集合：deadlock ⊂ unsafe，safe ∩ deadlock = ∅。

單一資源：Resource-Allocation Graph 與 Claim Edge

如果每種資源都只有一個（例如一台印表機、一台掃描器），可以不用銀行家演算法，直接在 Resource-Allocation Graph（資源配置圖，RAG）上判斷。RAG 裡圓形是行程、方形是資源，原本有兩種邊：

  • Request edge（請求邊）P → R：行程正在等這個資源。
  • Assignment edge（配置邊）R → P：資源已經配給這個行程。

為了「避免」，再多加一種 Claim Edge（宣告邊）P ⇢ R：行程將來可能會要這個資源，畫成虛線。所有 claim edge 必須在行程開始執行前就宣告好。之後狀態會這樣轉換：

  • 行程真的提出請求：claim edge → request edge。
  • 資源配給它：request edge → assignment edge。
  • 行程釋放資源：assignment edge → 變回 claim edge（以後還可能再要）。

判斷規則只有一條：P 請求 R 時，假設把這條邊改成 assignment edge R → P，如果圖中（連同 claim edge 一起看）出現環，就不給，P 等待；沒有環才配置。因為環代表「將來有可能形成循環等待」，而單一資源時，有環就等於 unsafe。

反過來，如果是 P1 請求 R2，配置後 P1 同時握有 R1、R2，P1 沒有任何往外的邊，不會有環，可以給。P1 做完把兩個都還回來，P2 再拿。

偵測環用 DFS，圖上有 n 個行程時，邊數是 O(n²) 級，所以檢查一次是 O(n²)。這個方法的限制也很明顯：只要某種資源有多個（例如 3 台印表機），「有環」就不一定代表 unsafe，必須改用銀行家演算法。

銀行家演算法的資料結構

設系統有 n 個行程、m 種資源，每種資源可以有很多個。銀行家演算法用四個陣列記錄狀態：

名稱大小意義
AvailablemAvailable[j] = 資源 j 現在還剩幾個
Maxn × mMax[i][j] = Pi 宣告最多會要幾個資源 j（執行前就要宣告）
Allocationn × mAllocation[i][j] = Pi 現在已經拿到幾個資源 j
Needn × mNeed[i][j] = Pi 最多還會再要幾個資源 j
 
Need[i][j] = Max[i][j] − Allocation[i][j]
資源 j 的總量 = Available[j] + Σ Allocation[i][j]（對所有行程 i 加總）

比較向量時用「每一項都 ≤」：X ≤ Y 代表 X[j] ≤ Y[j] 對所有 j 都成立。例如 (1 2 1) ≤ (2 2 2) 成立，但 (3 0 0) ≤ (2 2 2) 不成立（A 那一項 3 > 2），就算另外兩項很小也一樣。

本頁的例子

5 個行程 P0～P4、3 種資源 A、B、C，總量是 A = 9、B = 6、C = 7。目前已配置出去的加總是 (7 4 5)，所以 Available = (9 6 7) − (7 4 5) = (2 2 2)。

行程Allocation（A B C）Max（A B C）Need = Max − Allocation
P01 1 05 3 24 2 2
P12 0 13 2 21 2 1
P20 2 12 4 32 2 2
P33 0 24 1 41 1 2
P41 1 16 3 35 2 2

考題通常只給 Allocation 和 Max（有時給總量而不給 Available），第一步一定是自己算出 Need 和 Available。算錯 Need 後面全錯，所以寫完可以用「Available + 所有 Allocation = 總量」驗算一次。

看程式碼：資料結構、Need 與向量比較
全域陣列、computeNeed()、lessEq()
#define N 10                                   /* 最多行程數 */
#define M 10                                   /* 最多資源種類數 */

int n, m;                                      /* n 個行程、m 種資源 */
int Available[M];                              /* 每種資源目前還剩幾個 */
int Max[N][M];                                 /* 每個行程宣告的最大需求 */
int Allocation[N][M];                          /* 每個行程目前已經拿到的 */
int Need[N][M];                                /* 還可能再要的 = Max - Allocation */

void computeNeed(void) {
  for (int i = 0; i < n; i++)
    for (int j = 0; j < m; j++)
      Need[i][j] = Max[i][j] - Allocation[i][j];
}

/* 向量比較：a 的每一項都 <= b 才算 a <= b */
int lessEq(const int a[], const int b[]) {
  for (int j = 0; j < m; j++)
    if (a[j] > b[j]) return 0;
  return 1;
}

安全演算法：找出安全序列

Safety Algorithm（安全演算法）回答「現在這個狀態安不安全」。它模擬「讓行程一個一個跑完」：手上先有 Available 這麼多資源，找一個「就算把剩下的需求全部要滿也給得起」的行程，假設它跑完歸還資源，手上的資源就變多，再找下一個。

  1. Work = Available；所有 Finish[i] = false。Work 代表「模擬過程中手上有多少資源」。
  2. 找一個 i，滿足 Finish[i] == false 且 Need[i] ≤ Work。找不到就跳到第 4 步。
  3. Work = Work + Allocation[i]，Finish[i] = true，把 Pi 接到安全序列後面，回到第 2 步。
  4. 如果所有 Finish[i] 都是 true，狀態是 safe；否則是 unsafe。

第 3 步加回的是 Allocation 而不是 Need：Pi 從 Work 借走 Need[i]、跑完後把原本的 Allocation[i] 加上借走的 Need[i] 一起歸還，淨效果就是 Work 多了 Allocation[i]。為什麼「只要找到一個能跑完的就先讓它跑」不會錯過答案？因為讓任何一個行程跑完都只會讓 Work 變大，原本做得完的行程之後一定還做得完，所以選誰先都不會把自己逼進死路，只會影響序列長什麼樣子。

例子：每輪從 P0 開始找

用上面的例子，Work 從 (2 2 2) 開始。考研題目常要求「多個行程都可以時，編號小的優先」，等於每一輪都從 P0 開始往下找第一個做得完的：

輪檢查（Need vs Work）選中Work 變成
1P0 (4 2 2) vs (2 2 2)：A 不夠；P1 (1 2 1) ≤ (2 2 2)P1(2 2 2) + (2 0 1) = (4 2 3)
2P0 (4 2 2) ≤ (4 2 3)P0(4 2 3) + (1 1 0) = (5 3 3)
3P2 (2 2 2) ≤ (5 3 3)P2(5 3 3) + (0 2 1) = (5 5 4)
4P3 (1 1 2) ≤ (5 5 4)P3(5 5 4) + (3 0 2) = (8 5 6)
5P4 (5 2 2) ≤ (8 5 6)P4(8 5 6) + (1 1 1) = (9 6 7)

5 個行程都完成，狀態是 safe，安全序列 <P1, P0, P2, P3, P4>。最後的 Work = (9 6 7) 正好是資源總量，這是一個很好用的驗算：所有人都把資源還回來了，手上當然是全部。

如果是 unsafe

同樣的 Max 和 Allocation，如果 Available 只有 (1 1 2)：P0、P1、P2 都至少有一項不夠，只有 P3 的 Need (1 1 2) ≤ (1 1 2)，跑完 Work = (4 1 4)。這時 P0、P1、P2、P4 的 Need 在 B 那一項都是 2，而 Work 的 B 只有 1，再也找不到人，狀態是 unsafe。只差了 A、B 各 1 個，結果就完全不同，這也說明為什麼每次配置前都要重新試算。

時間複雜度：O(m · n²)

最壞情況每一輪只完成一個行程，總共 n 輪；每一輪最多要檢查 n 個行程；每次檢查是比較兩個長度 m 的向量。所以是 n × n × m = O(m · n²)。以 n = 5、m = 3 來說，最壞大約是 (5 + 4 + 3 + 2 + 1) × 3 = 45 次數字比較，量很小；但真實系統有上百個行程，而且每一次資源請求都要跑一次，這就是銀行家演算法在實務上很少直接使用的原因之一。

看程式碼：安全演算法（每輪從 P0／接著往下掃）
isSafe()：每輪從 P0 開始找第一個做得完的
/* 安全演算法：安全回傳 1，並把安全序列放進 seq[]；不安全回傳 0 */
int isSafe(int seq[]) {
  int Work[M], Finish[N] = {0}, count = 0;
  for (int j = 0; j < m; j++) Work[j] = Available[j];
  while (count < n) {
    int found = -1;
    for (int i = 0; i < n && found == -1; i++)   /* 每輪從 P0 開始，找第一個做得完的 */
      if (!Finish[i] && lessEq(Need[i], Work)) found = i;
    if (found == -1) return 0;                    /* 沒有人做得完：unsafe */
    for (int j = 0; j < m; j++)
      Work[j] += Allocation[found][j];            /* 它做完會歸還全部資源 */
    Finish[found] = 1;
    seq[count++] = found;
  }
  return 1;
}
isSafeSweep()：找到後不回頭，掃到底再從頭
int isSafeSweep(int seq[]) {
  int Work[M], Finish[N] = {0}, count = 0, progress = 1;
  for (int j = 0; j < m; j++) Work[j] = Available[j];
  while (progress) {                              /* 整輪都沒人做得完才停 */
    progress = 0;
    for (int i = 0; i < n; i++)
      if (!Finish[i] && lessEq(Need[i], Work)) {
        for (int j = 0; j < m; j++) Work[j] += Allocation[i][j];
        Finish[i] = 1;
        seq[count++] = i;
        progress = 1;
      }
  }
  return count == n;
}

安全序列不唯一

第 2 步只說「找一個」，沒有規定找哪一個，所以同一個狀態可能有很多安全序列。上面的例子如果改成「找到一個之後不回頭，接著往下掃，掃到底再從 P0 開始」（上一節程式碼的第二個頁籤），結果是：

掃描方式過程安全序列
每輪從 P0 開始（編號小的優先）P1 完成後回頭，P0 這時做得完<P1, P0, P2, P3, P4>
接著往下掃P1 完成後繼續看 P2、P3、P4，都做得完；第二輪才輪到 P0<P1, P2, P3, P4, P0>

兩個都是正確的安全序列。實際上這個狀態總共有 50 種安全序列（已用程式枚舉 5! = 120 種排列驗證）：第一個只能是 P1 或 P2，因為一開始只有它們的 Need ≤ (2 2 2)；之後 Work 夠大，大部分順序都行。

這帶來兩個考試重點：

  • 題目有規定挑選規則就照規則（最常見是「編號小的優先」），否則答案可能和標準答案不同，但只要每一步都滿足 Need ≤ Work 就是對的。
  • 判斷 safe／unsafe 的結論和掃描方式無關：只要存在任何一個安全序列就是 safe。前面說過，先讓誰跑完都只會讓 Work 變大，所以用哪種掃描方式都不會誤判。

資源請求演算法

安全演算法只是「檢查」。真正在系統裡運作的是 Resource-Request Algorithm（資源請求演算法）：Pi 提出請求向量 Requesti 時，依序做：

  1. 如果 Requesti ≤ Need[i] 不成立：錯誤。行程要的比它當初宣告的最大需求還多，違反約定，直接報錯（不是等待）。
  2. 如果 Requesti ≤ Available 不成立：資源現在不夠，Pi 等待。
  3. 假裝配置：Available −= Requesti；Allocation[i] += Requesti；Need[i] −= Requesti。
  4. 對這個假想的新狀態跑安全演算法：safe 就真的配置；unsafe 就把第 3 步復原，Pi 等待。

前兩步的順序與結果要分清楚：超過 Need 是「錯誤」，超過 Available 是「等待」。第 4 步才是銀行家演算法的精神：就算資源現在拿得出來，也可能不給。

例子一：P3 請求 (1 0 1)，可以配置

  1. (1 0 1) ≤ Need[P3] = (1 1 2)，通過。
  2. (1 0 1) ≤ Available = (2 2 2)，通過。
  3. 假裝配置：Available = (1 2 1)，Allocation[P3] = (4 0 3)，Need[P3] = (0 1 1)。
  4. 試算：Work = (1 2 1)，P0 不夠，P1 (1 2 1) 可以 → (3 2 2)；P0 的 A 要 4 還不夠，P2 (2 2 2) 可以 → (3 4 3)；P0 還不夠，P3 (0 1 1) 可以 → (7 4 6)；P0 (4 2 2) 可以 → (8 5 6)；P4 (5 2 2) 可以 → (9 6 7)。safe，安全序列 <P1, P2, P3, P0, P4>，配置。

例子二：P4 請求 (2 0 0)，資源夠但不給

  1. (2 0 0) ≤ Need[P4] = (5 2 2)，通過。
  2. (2 0 0) ≤ Available = (2 2 2)，通過，資源拿得出來。
  3. 假裝配置：Available = (0 2 2)，Allocation[P4] = (3 1 1)，Need[P4] = (3 2 2)。
  4. 試算：Work = (0 2 2)，A 一個都不剩，而 5 個行程的 Need 在 A 那一項都至少是 1（4、1、2、1、3），誰都跑不完：unsafe。復原，P4 等待。

例子二是考題最愛的陷阱：只檢查前兩步就會回答「可以配置」。P4 一口氣把 A 全拿走，萬一大家都要到 Max，沒有人能先做完歸還 A，就會死結。

另外兩種結果

  • P1 請求 (0 3 0)：Need[P1] = (1 2 1)，B 要 3 > 2，超過宣告的最大需求，錯誤。
  • P0 請求 (3 0 0)：沒超過 Need[P0] = (4 2 2)，但 A 要 3 > Available 的 2，等待。

資源請求演算法的成本是前兩步 O(m)，加上一次安全演算法 O(m · n²)，所以每次請求是 O(m · n²)。

看程式碼：資源請求演算法
request()：先檢查、假裝配置、試算安全性
/* 資源請求演算法：P[p] 要求 Request[]
   回傳 1 = 配置成功、0 = 會變 unsafe 要等、-1 = 超過宣告的最大需求、-2 = 資源不夠要等 */
int request(int p, const int Request[], int seq[]) {
  if (!lessEq(Request, Need[p])) return -1;      /* 要的比當初宣告的還多：錯誤 */
  if (!lessEq(Request, Available)) return -2;    /* 現在的資源不夠：只能等 */
  for (int j = 0; j < m; j++) {                  /* 先假裝配置給它 */
    Available[j] -= Request[j];
    Allocation[p][j] += Request[j];
    Need[p][j] -= Request[j];
  }
  if (isSafe(seq)) return 1;                     /* 配置後仍安全：真的給 */
  for (int j = 0; j < m; j++) {                  /* 不安全：復原，P[p] 等待 */
    Available[j] += Request[j];
    Allocation[p][j] -= Request[j];
    Need[p][j] += Request[j];
  }
  return 0;
}

動手操作

上面三個輸入框依序是 Available、Max、Allocation：同一列的數字用空白隔開，不同行程用分號隔開，第一列是 P0（最多 6 個行程、4 種資源，每個數字 0～20）。Need 會自動算出來。按「安全檢查」逐步看安全演算法：藍色是正在比較的 Need，紅色是不夠的那一項，紫色是剛加回 Work 的 Allocation；「掃描：每輪從 P0」可以切換成「接著往下」，比較兩種安全序列。

最後兩個輸入框是請求：行程編號（例如 3 代表 P3）和請求向量，按「提出請求」會先做兩個檢查，再假裝配置、試算安全性（請求的試算固定用「每輪從 P0」）。「請求被拒」是上面的例子二，「請求超過 Need」是報錯的情況。

優缺點與死結偵測的比較

銀行家演算法的優缺點

  • 優點：不需要像預防那樣限制行程申請資源的方式（不用一次要齊、不用照編號），資源使用率比預防高，又保證不會死結。
  • 缺點一：要事先知道 Max。大部分程式執行前根本不知道自己最多會要多少資源，宣告太大又會讓演算法過度保守。
  • 缺點二：行程數、資源數要固定。行程隨時建立、結束，資源也可能故障，演算法假設的條件在真實系統中常常不成立。
  • 缺點三：太保守、太花時間。unsafe 不一定死結，卻一律擋下，行程常常要等；每次請求都要跑 O(m · n²)。
  • 缺點四：要求行程在有限時間內歸還資源，否則序列中的後續行程永遠等不到。

和死結偵測的比較

死結偵測在資源有多個時用的演算法，長得幾乎和安全演算法一樣，只有兩處不同：比較時用的是每個行程現在正在等的 Request，而不是最壞情況的 Need；而且 Allocation 全是 0 的行程一開始就當作 Finish = true（它手上沒資源，不可能卡住別人）。跑完之後 Finish 仍是 false 的行程，就是已經陷入死結的行程。換句話說，避免問的是「最壞情況下會不會出事」，偵測問的是「現在是不是已經出事了」。

實務上，資料庫系統的交易常用偵測（等待圖有環就讓某個交易回滾），一般作業系統則多半選擇忽略；銀行家演算法在考試中的地位遠高於實務，但它提供的「試算後只停在安全狀態」想法，在資源預留、批次排程等場合仍然看得到。

易錯點

  • 系統進入 unsafe state 就已經死結了 → unsafe 只是「無法保證」不死結；行程實際要的可能比 Max 少，仍可能全部做完 例題
  • Request ≤ Available 就可以直接配置 → 還要假裝配置、跑安全演算法，unsafe 就不給 例題
  • Request 超過 Need 時讓行程等待 → 超過 Need 是違反宣告，屬於錯誤；超過 Available 才是等待 例題
  • 行程完成後 Work 加上它的 Need（或 Max） → 加上的是 Allocation：它借走的 Need 跑完會連同原本的 Allocation 一起還，淨增加就是 Allocation 例題
  • 拿 Max 直接和 Work 比較 → 要先算 Need = Max − Allocation，比較的是 Need ≤ Work 例題
  • 安全序列只有一個，和標準答案不同就是錯 → 安全序列通常很多個；題目規定「編號小的優先」時才有唯一答案 例題
  • 單一資源時，請求的資源空著就可以給 → 要連同 claim edge 一起找環，會形成環就不給 例題
