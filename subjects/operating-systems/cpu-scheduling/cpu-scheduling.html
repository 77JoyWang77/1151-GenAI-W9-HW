CPU Scheduling Algorithms CPU 排程演算法下一個給誰用 CPU，決定了大家要等多久

Ch3 CPU Scheduling 難度 FCFS SJF / SRTF Round Robin Gantt chart

為什麼需要 CPU 排程

一個程式執行時，通常是「算一下 → 等 I/O → 再算一下 → 再等 I/O」交替進行，前者叫 CPU Burst（CPU 爆發期），後者叫 I/O burst。如果 CPU 只服務一個程式，它在等硬碟、等網路、等使用者輸入的時候，CPU 就只能空轉。Multiprogramming（多工）的做法是讓記憶體裡同時放好幾個行程，一個去等 I/O，就把 CPU 交給另一個，讓 CPU 盡量一直有事做。

這時就需要決定：好幾個行程都準備好了，下一個要給誰用 CPU？這就是 CPU Scheduler（CPU 排程器）的工作。排程器從 ready queue 中挑一個行程，再由 Dispatcher（分派器）負責切換：存下舊行程的狀態、載入新行程的狀態、跳到使用者模式開始執行。切換所花的時間叫 dispatch latency，這段時間 CPU 沒在做有用的工作，所以切換太頻繁也不好。

排程的時機有四種：(1) running → waiting（例如發出 I/O 要求）；(2) running → ready（例如計時器中斷）；(3) waiting → ready（I/O 完成）；(4) 行程結束。如果只在 (1) 和 (4) 這種「行程自己讓出 CPU」的時候排程，叫 Nonpreemptive（不可搶先）；如果 (2)、(3) 也會排程，也就是可以中途把 CPU 搶走，叫 Preemptive（可搶先）。現代作業系統都是可搶先的，但搶先會帶來共享資料的同步問題，這是之後「行程同步」要處理的。

排程好不好：五個指標

指標定義希望
CPU utilization（CPU 使用率）CPU 忙碌的時間比例越高越好
Throughput（產出量）單位時間完成的行程數越高越好
Turnaround time（周轉時間）從到達到完成的總時間越短越好
Waiting time（等待時間）待在 ready queue 裡的時間總和越短越好
Response time（回應時間）從到達到第一次拿到 CPU 的時間越短越好（互動系統最在意）

考試最常算的是等待時間和周轉時間。只考慮 CPU、不考慮 I/O 時，它們有固定的關係：

周轉時間 = 完成時間 − 到達時間
等待時間 = 周轉時間 − burst 時間
回應時間 = 第一次執行的時間 − 到達時間

排程演算法改變的只是「誰先誰後」，每個行程真正用 CPU 的時間（burst）不會變，所以排程演算法真正能影響的就是等待時間。這也是為什麼比較演算法時，最常看平均等待時間。

FCFS：先到先服務

First-Come, First-Served（先到先服務，FCFS）最簡單：ready queue 就是一般的 FIFO queue，誰先到誰先用，用到做完為止，不可搶先。實作容易、也公平，但有個嚴重的問題：如果一個很長的行程先到，後面一堆短行程都得乾等。

這種「一台慢車擋住後面一整排車」的現象叫 Convoy Effect（護航效應）。在真實系統裡，一個 CPU 密集的行程佔住 CPU 時，所有 I/O 密集的行程都卡在 ready queue，I/O 裝置也跟著閒置，CPU 和裝置的使用率都變差。所以 FCFS 很少單獨使用，但它常是其他演算法在平手時的規則。

SJF 與 SRTF：短的先跑

圖 2 已經暗示了答案：要讓平均等待時間最小，就讓短的先跑。Shortest-Job-First（最短工作優先，SJF）每次從 ready 的行程中挑 burst 最短的來執行。可以證明：當所有行程同時到達時，SJF 的平均等待時間是所有排法中最小的。直覺是交換論證：如果長的排在短的前面，把兩者交換，短的少等了「長的 burst」、長的多等了「短的 burst」，總等待時間一定下降。

SJF 有兩種版本：

  • 不可搶先的 SJF：一旦開始就做到完，新到達的行程再短也要等。
  • 可搶先的 SJF，叫 Shortest-Remaining-Time-First（最短剩餘時間優先，SRTF）：每當有新行程到達，就比較它的 burst 和正在執行的行程剩餘的時間，新來的比較短就搶走 CPU。

例子：同一組行程，SJF 與 SRTF

P1（到達 0，burst 7）、P2（到達 2，burst 4）、P3（到達 3，burst 1）、P4（到達 5，burst 6）。

演算法甘特圖（時間：行程）各行程等待時間平均等待
SJF（不可搶先）0–7 P1、7–8 P3、8–12 P2、12–18 P4P1 = 0、P2 = 6、P3 = 4、P4 = 74.25
SRTF（可搶先）0–2 P1、2–3 P2、3–4 P3、4–7 P2、7–12 P1、12–18 P4P1 = 5、P2 = 1、P3 = 0、P4 = 73.25

SRTF 在時間 2 時，P2 的 4 比 P1 剩下的 5 短，所以搶先；時間 3 時 P3 只要 1，又搶走 P2。結果平均等待比 SJF 少了 1（約少 24%）。代價是切換次數變多（SJF 切換 3 次，SRTF 切換 5 次）。

問題：怎麼知道下一個 burst 多長？

SJF 的致命問題是：真正執行之前，沒有人知道一個行程下一次會用 CPU 多久。實務上只能預測，最常用的是 Exponential Averaging（指數平均）：用上一次實際的 burst tn 和上一次的預測值 τn 加權平均。

τ(n+1) = α · t(n) + (1 − α) · τ(n)      0 ≤ α ≤ 1
α = 0：完全不看最近的實際值（預測永遠不變）
α = 1：只看上一次的實際值
α = 1/2：最近一次和過去的歷史各佔一半

展開後可以看出，越久以前的實際值，權重是 (1 − α) 的越高次方，影響越小，所以這個公式「記得歷史，但更相信最近」。

看程式碼：非搶先與搶先排程（FCFS / SJF / Priority / SRTF）
nonPreemptive()：FCFS、SJF、Priority
int key(int i, int alg) {                      /* 挑選依據：值越小越先 */
  if (alg == FCFS) return p[i].arrival;
  if (alg == SJF) return p[i].remain;          /* SJF / SRTF 看剩下的 burst */
  return p[i].priority;
}

/* 在時間 t 已到達、還沒做完的行程中，挑 key 最小的；平手時先到的優先 */
int pick(int t, int alg) {
  int best = -1;
  for (int i = 0; i < n; i++) {
    if (p[i].remain == 0 || p[i].arrival > t) continue;
    if (best == -1 || key(i, alg) < key(best, alg) ||
        (key(i, alg) == key(best, alg) && p[i].arrival < p[best].arrival)) best = i;
  }
  return best;
}

void nonPreemptive(int alg) {
  int t = 0, done = 0;
  reset();
  while (done < n) {
    int i = pick(t, alg);
    if (i == -1) { gantt[t++] = -1; continue; }   /* 沒有行程到達：CPU 閒置 */
    p[i].start = t;
    while (p[i].remain > 0) {                  /* 一旦開始就做到完 */
      gantt[t++] = i;
      p[i].remain--;
    }
    p[i].finish = t;
    done++;
  }
  len = t;
}
preemptive()：SRTF、搶先式 Priority
void preemptive(int alg) {
  int t = 0, done = 0, cur = -1;
  reset();
  while (done < n) {
    int i = pick(t, alg);
    if (cur != -1 && p[cur].remain > 0 && key(cur, alg) <= key(i, alg)) i = cur;   /* 平手不搶 */
    if (i == -1) { gantt[t++] = -1; continue; }
    if (p[i].start == -1) p[i].start = t;
    gantt[t++] = i;                            /* 每個時間單位都重新挑一次 */
    if (--p[i].remain == 0) { p[i].finish = t; done++; }
    cur = i;
  }
  len = t;
}

Priority 排程與飢餓

Priority Scheduling（優先權排程）替每個行程定一個優先權，每次挑優先權最高的執行；本頁約定數字越小越優先（不同題目的約定可能相反，作答前要先看清楚）。優先權可以由系統內部決定（例如記憶體需求、I/O 比例），也可以由外部決定（例如付費等級）。SJF 其實就是「以預測的 burst 當優先權」的特例。

Priority 一樣有不可搶先和可搶先兩種。上面同一組行程若優先權為 P1 = 3、P2 = 1、P3 = 4、P4 = 2：

版本甘特圖平均等待
不可搶先0–7 P1、7–11 P2、11–17 P4、17–18 P36.25
可搶先0–2 P1、2–6 P2、6–12 P4、12–17 P1、17–18 P36.25

兩個版本的平均等待剛好一樣，但個別行程的感受差很多：可搶先時 P2 一到就執行、等待 0，P1 卻等了 10；不可搶先時 P1 等待 0，P2 等了 5。

Priority 最大的問題是 Starvation（飢餓）：只要一直有高優先權的行程進來，低優先權的行程可能永遠輪不到。標準解法是 Aging（老化）：行程在 ready queue 裡每等一段時間，優先權就提高一點，等得夠久一定會輪到。SJF 也有同樣的飢餓問題，因為長工作可能一直被新來的短工作插隊。

Round Robin：輪流使用

Round Robin（輪轉法，RR）是為分時系統設計的：規定一個 Time Quantum（時間配額） q，ready queue 用 FIFO，每個行程最多連續跑 q 個時間單位；時間到還沒做完，就被計時器中斷、排到 queue 的最後面。所以 RR 一定是可搶先的。

有 n 個行程時，每個行程最多等 (n − 1) · q 就會再輪到一次，回應時間有上限，這正是互動系統要的。上面那組行程用 q = 3：甘特圖是 0–3 P1、3–6 P2、6–7 P3、7–10 P1、10–13 P4、13–14 P2、14–15 P1、15–18 P4，平均等待 6.50，比 SRTF 的 3.25 高，但平均回應時間只有 2.25。

RR 的慣例：時間片用完的那一刻，如果剛好有新行程到達，新到的先排進 queue，被搶走的再排到它後面。不同題目可能有不同約定，題目沒說時照這個慣例，並在答案中寫出來。

q 要多大？

  • q 太大：每個行程都在一個 quantum 內做完，RR 就退化成 FCFS。
  • q 太小：切換太頻繁。例如 context switch 要 0.1 ms，q = 1 ms 時，約 9% 的時間浪費在切換（0.1 / 1.1）；q = 10 ms 時只剩約 1%。
  • 經驗法則：q 要比大約 80% 的 CPU burst 長，讓大多數行程在一個 quantum 內做完；q 通常遠大於 context switch 時間。
看程式碼：roundRobin()
roundRobin()：time quantum = q
void roundRobin(int q) {
  int queue[TMAX], front = 0, rear = 0;
  int t = 0, done = 0, next = 0;               /* next：下一個還沒進 queue 的行程（依到達時間排序） */
  reset();
  while (done < n) {
    while (next < n && p[next].arrival <= t) queue[rear++] = next++;   /* 新到的放進 queue 尾端 */
    if (front == rear) { gantt[t++] = -1; continue; }
    int i = queue[front++];
    if (p[i].start == -1) p[i].start = t;
    int run = p[i].remain < q ? p[i].remain : q;   /* 最多跑一個 time quantum */
    for (int k = 0; k < run; k++) { gantt[t++] = i; p[i].remain--; }
    while (next < n && p[next].arrival <= t) queue[rear++] = next++;   /* 這段時間內到達的先排進去 */
    if (p[i].remain > 0) queue[rear++] = i;    /* 還沒做完：排到 queue 最後面 */
    else { p[i].finish = t; done++; }
  }
  len = t;
}

動手操作

每個行程寫成「到達時間 burst [優先權]」，用分號隔開，例如預設的 0 7 3; 2 4 1; 3 1 4; 5 6 2 就是上面的例子，行程依序命名為 P1、P2……。選一種演算法按播放，可以看到 ready queue 怎麼變、甘特圖怎麼長出來，最後算出平均等待、周轉與回應時間。Round Robin 的 q 在第二個輸入框設定；按「convoy 範例」可以看到圖 2 的情況。

多層佇列與多層回饋佇列

真實系統裡行程的性質差很多：互動式的前景行程要回應快，批次的背景行程只要最後做完就好。Multilevel Queue（多層佇列）把 ready queue 分成好幾個，每個 queue 有自己的演算法（例如前景用 RR、背景用 FCFS），queue 之間再用固定優先權或分配 CPU 時間比例來排。缺點是行程一開始被分到哪個 queue 就固定了。

Multilevel Feedback Queue（多層回饋佇列，MLFQ）允許行程在 queue 之間移動，用「過去的行為」來推測它是哪一種行程：

  • 新行程先進最高優先權的 Q0，quantum 很小。
  • 用完整個 quantum 還沒做完，代表它可能是 CPU 密集，就降到下一層，quantum 變大、優先權變低。
  • 很快就去做 I/O 的行程會一直留在上層，回應快。
  • 在低層等太久的行程可以往上升（aging），避免飢餓。

MLFQ 不需要事先知道 burst 長度，卻能近似 SJF「短的先跑」的效果，所以是最通用的設計；代價是參數很多（幾層、各層的演算法與 quantum、升降規則），調整起來也最複雜。

整理：演算法比較

以本頁同一組行程（P1：0/7、P2：2/4、P3：3/1、P4：5/6）比較：

演算法可搶先平均等待平均回應優點缺點
FCFS否5.005.00最簡單、公平convoy effect
SJF否4.254.25同時到達時平均等待最小不知道 burst、長工作飢餓
SRTF是3.251.75平均等待最小切換多、長工作飢餓

可以看到沒有一種演算法在所有指標都最好：SRTF 的平均等待最低，RR 的回應時間有保證，FCFS 最簡單。考題常問「哪一種適合互動系統」（RR）、「哪一種平均等待最小」（SRTF，不可搶先時是 SJF）、「哪些會飢餓」（SJF、SRTF、Priority）。

易錯點

  • 等待時間 = 開始執行的時間 − 到達時間 → 那是回應時間；可搶先時行程會被中斷再等，等待時間要用「完成 − 到達 − burst」 例題
  • SJF 不可能飢餓，因為每個工作終究會變成最短的 → 只要一直有更短的新工作到達，長工作就可能永遠等下去 例題
  • RR 的 quantum 越小越好，回應越快 → q 太小時 context switch 的比例變高；q 太大則退化成 FCFS 例題
  • RR 時間片用完時，被中斷的行程和新到的行程誰先排都一樣 → 順序會改變甘特圖；慣例是新到的先排，題目有規定就照題目 例題
  • SRTF 只在行程完成時才重新挑選 → 每當有新行程到達都要比較「新行程的 burst」和「目前行程的剩餘時間」 例題
