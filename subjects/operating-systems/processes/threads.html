為什麼需要執行緒

想像一個網頁伺服器：每秒有上百個連線進來，每個連線都要讀檔、等網路、送回資料。如果整個伺服器只有一條執行流程，它在等某個連線的硬碟 I/O 時，其他連線全都只能排隊。傳統的解法是每來一個連線就 fork() 一個新的行程去處理，但行程很「重」：每個行程都有自己的位址空間、頁表、開啟檔案表，建立和切換都要花不少時間，而且行程之間要分享資料還得透過 IPC。行程本身的狀態與 PCB 在 Process Concept 行程與行程狀態（籌備中）詳細說明。

Thread（執行緒）就是把「執行」從行程裡拆出來：一個行程裡可以有好幾條執行流程，它們共用同一個位址空間與資源，各自有自己的執行狀態。行程變成「資源的容器」，thread 變成「CPU 排程的基本單位」。

多執行緒帶來四個好處：

好處意思例子
Responsiveness（回應性）一個 thread 卡在耗時的工作時，其他 thread 還能回應使用者瀏覽器下載檔案時，畫面照樣能捲動
Resource sharing（資源共享）同一行程的 thread 天生共用記憶體和檔案，不用另外設定 shared memory 或 message passing多個 thread 讀同一份快取資料
Economy（經濟）建立 thread、在 thread 間切換，都比行程便宜很多不用複製位址空間、不用換頁表
Scalability（延展性）多核心上不同 thread 可以真的同時跑4 個 thread 各算四分之一的陣列

代價是：因為共用記憶體，多個 thread 同時改同一筆資料就會出錯，需要同步機制；這也是後面「行程同步」一整章要處理的問題。

共享什麼、各自擁有什麼

這是考題最愛出的觀念。判斷原則只有一條：要讓不同 thread 執行到不同地方、呼叫不同函式，就得各自擁有；其餘屬於行程的東西都共用。

每個 thread 各自擁有同一行程的 thread 共用
thread IDcode section（程式碼）
program counter（PC）data section（global、static 變數）
register set（暫存器）heap（malloc 出來的空間）
stack（區域變數、參數、返回位址）開啟的檔案、signal 處理方式、位址空間（同一張 page table）

為什麼 stack 一定要分開？因為每個 thread 有自己的函式呼叫鏈：thread A 正在 f() 裡、thread B 正在 g() 裡，兩邊的區域變數和返回位址如果放在同一個 stack，一 push 一 pop 就會互相蓋掉。所以「thread 共用 stack」永遠是錯的敘述。

切換成本：為什麼 thread 比較便宜

從 thread A 切到同一行程的 thread B，只要存下 A 的暫存器、PC、stack pointer，再載入 B 的；兩者在同一個位址空間，page table 不用換（page-table base register 不變），TLB 裡的對應也還能用，不必清掉。切到另一個行程則要換頁表，TLB 若沒有 ASID（位址空間編號）就得整個清空，之後一段時間的記憶體存取都會變慢（TLB 的運作見 Paging and TLB 分頁與 TLB）。

注意考題的陷阱：「thread 切換快，因為它們共用 page table 和 user stack」是錯的，前半對、後半錯。同理，「每個 thread 有自己的 page table」也是錯的。

看程式碼：pthread_create / pthread_join（分段加總）
parallelSum()：4 個 thread 各加四分之一
#define NT 4
#define LEN 1000
int data[LEN];                 /* data section：所有 thread 共用 */
long partial[NT];              /* 每個 thread 寫自己的那一格，不會互相干擾 */

void *sumPart(void *arg) {
  int id = *(int *)arg;        /* 參數指向 main 裡 ids[] 的一格 */
  long s = 0;                  /* 區域變數在這個 thread 自己的 stack 上 */
  for (int i = id * (LEN / NT); i < (id + 1) * (LEN / NT); i++) s += data[i];
  partial[id] = s;
  return NULL;
}

long parallelSum(void) {
  pthread_t tid[NT];
  int ids[NT];                 /* 每個 thread 一個獨立的參數，不能共用同一個 i */
  for (int i = 0; i < NT; i++) {
    ids[i] = i;
    pthread_create(&tid[i], NULL, sumPart, &ids[i]);
  }
  long total = 0;
  for (int i = 0; i < NT; i++) {
    pthread_join(tid[i], NULL);  /* 等第 i 個 thread 結束（synchronous threading） */
    total += partial[i];
  }
  return total;
}

這段程式裡，data[]、partial[] 是 global，所有 thread 看到的是同一份；s 是區域變數，每個 thread 在自己的 stack 上各有一個，不會互相干擾。每個 thread 只寫自己那一格 partial[id]，所以不需要鎖。另一個常見錯誤是把迴圈變數 &i 直接傳給所有 thread：thread 真正讀取時 i 可能已經被 main 改掉，所以要用 ids[] 每個 thread 一格。

多核心：並行與平行

兩個常被混用、考試卻嚴格區分的詞：

  • Concurrency（並行）：多個工作都在推進。單核心靠快速切換，讓每個 thread 輪流跑一小段，就能做到。
  • Parallelism（平行）：同一時刻真的有多個工作同時在執行，需要多顆核心（或多個處理器）。

所以「沒有 parallelism 也可以有 concurrency」是對的，「單核心系統無法支援 concurrent 計算」是錯的。反過來，有 parallelism 一定有 concurrency。

平行化的方式分兩種：Data Parallelism（資料平行）把同一份資料切塊、每個核心做同樣的運算（例如上面的分段加總）；Task Parallelism（工作平行）把不同的工作分給不同核心（例如一個 thread 解碼影片、一個處理音訊）。寫多核心程式的難處在於：怎麼切工作、讓負擔平均、資料怎麼分、thread 之間的相依與同步，以及平行程式更難測試除錯。

Amdahl's Law：加核心的上限

核心數加倍，速度不會跟著加倍，因為程式裡總有一部分只能序列執行。設序列部分佔原本執行時間的比例為 S、核心數為 N：

speedup ≤ 1 / (S + (1 − S) / N)
N → ∞ 時，speedup → 1 / S

例：S = 10%。4 核心時 speedup = 1 / (0.1 + 0.9/4) ≈ 3.08，16 核心時 ≈ 6.4，核心多了 4 倍，speedup 只多約一倍；不管加多少核心都超不過 1 / 0.1 = 10 倍。再加上 thread 建立、同步、溝通的成本，實際值還會更低。所以「兩核心一定有兩倍加速」是錯的，「thread 越少效能一定越差」也是錯的：thread 數超過核心數或 I/O 等待的需要時，多出來的 thread 只會增加切換與搶鎖的負擔。Amdahl's Law 的推導和「比例要用執行時間而不是指令數」這個陷阱，在 CPU Time and CPI CPU 時間與 CPI 有一個例子，完整內容在 Amdahl's Law Amdahl 定律（籌備中）。

User Thread 與 Kernel Thread

thread 可以在兩個層次上實作：

  • User Thread（使用者層級執行緒）：由 user space 的 thread library 建立與管理，kernel 不知道它們的存在。建立、切換都只是函式呼叫，不用 trap 進 kernel，非常快；library 也可以用自己的排程策略（例如替同一行程的 thread 設不同優先權）。
  • Kernel Thread（核心層級執行緒）：由作業系統直接支援與排程，建立與切換都要經過 system call，比較慢；但 kernel 看得到每一個，可以個別排到不同核心上，一個 block 了也能改排別的。現代的 Linux、Windows、macOS 都支援。

最關鍵的一句話：CPU 只執行 kernel 排程的單位。user thread 要真正跑起來，一定要「搭」在某個 kernel thread 上。kernel 只看得到 kernel thread，所以一個 user thread 做 read() 這類 Blocking System Call（會阻塞的系統呼叫）時，kernel 卡住的是它所搭的那個 kernel thread，搭在同一個 kernel thread 上的其他 user thread 也跟著動不了。

比較User threadKernel thread
誰管理thread library（user space）kernel
建立／切換快，不用進 kernel慢，要 system call、mode switch
排程策略library 自訂，可依應用調整kernel 統一決定
一個 block同一 kernel thread 上的全部卡住只有自己卡住
多核心只能用到它所搭的 kernel thread 數那麼多顆每個都可以排到不同核心

兩邊各自要保存執行狀態：user thread 在 user mode 跑，有自己的 user stack 和 library 維護的控制區塊（TCB）；kernel thread 進入 kernel 執行 system call 時用的是自己的 kernel stack，kernel 也替它維護控制區塊（例如 Linux 的 task_struct）。user mode 和 kernel mode 不會共用同一個 stack，否則 user 程式就能竄改 kernel 的資料。

四種多執行緒模型

user thread 和 kernel thread 怎麼對應，決定了「一個 block 會不會拖累別人」與「能用到幾顆核心」。

Many-to-One

所有 user thread 對應到一個 kernel thread。thread 管理全在 user space，很有效率；但只要有一個 user thread 做 blocking system call，唯一的 kernel thread 就被卡住，整個行程都停住；而且同時只有一個 thread 能用 CPU，多核心完全派不上用場。早期的 Solaris Green Threads 就是這種，現在幾乎沒人用。

One-to-One

每個 user thread 都有自己的 kernel thread。一個 block，其他照跑；多個 thread 可以平行跑在不同核心上。缺點是每建立一個 user thread 就要建立一個 kernel thread，數量太多時拖累系統效能，所以有的系統會限制 thread 數。Linux 與 Windows 都採用 one-to-one，因為現代機器的核心多、kernel thread 也夠便宜。

Many-to-Many

M 個 user thread 多工到 N 個 kernel thread 上（N ≤ M），兼顧兩邊：程式可以開很多 user thread，又能平行執行，一個 block 時 library 可以把其他 user thread 放到別的 kernel thread 上。實作上 user thread 和 kernel thread 之間通常夾一層 LWP（Lightweight Process，輕量級行程）：對 library 來說它像一顆虛擬處理器，每個 LWP 背後接一個 kernel thread。

kernel thread 要配幾個很重要：少於核心數時，有些核心根本沒事做；剛好等於核心數時，只要有一個 block，那顆核心就閒著。所以 kernel thread 最好比核心數多。LWP 全被 block 時，有的系統用 Scheduler Activation（排程器啟動）：kernel 透過 upcall 通知 thread library「某個 thread 要 block 了」，並配給它一個新的 LWP，讓其他 user thread 繼續跑。many-to-many 很有彈性，但實作複雜，加上核心數變多後 one-to-one 已經夠用，現在主流系統很少採用。

Two-Level

many-to-many 的變形：大部分 user thread 一樣多工，但允許某些重要的 user thread 綁定（bound）到自己專屬的 kernel thread，保證它隨時有 kernel thread 可用。

模型kernel thread 數一個 thread 做 blocking call能否平行代表
Many-to-one1整個行程卡住不能Green Threads
One-to-one= user thread 數只有自己卡住能Linux、Windows
Many-to-manyN ≤ M只卡一個 LWP；LWP 全被卡時其他也要等能，最多 N 個舊版 Solaris
Two-levelN 個共用 + bound 的同 many-to-many；bound thread 不受影響能舊版 Solaris、IRIX

Contention Scope：誰跟誰搶

有 user thread 的系統其實有兩層排程：

  • PCS（Process-Contention Scope，行程競爭範圍）：thread library 決定同一個行程裡哪個 user thread 可以用 LWP。競爭對象只有同行程的 thread，通常依優先權、可搶先（高優先權的會搶走低優先權的）。
  • SCS（System-Contention Scope，系統競爭範圍）：kernel 決定全系統哪個 kernel thread 上哪顆 CPU。

one-to-one 的系統只有 SCS（user thread 直接就是 kernel thread）。Pthreads 用 pthread_attr_setscope() 指定 PTHREAD_SCOPE_PROCESS（PCS）或 PTHREAD_SCOPE_SYSTEM（SCS），Linux 和 macOS 只允許 PTHREAD_SCOPE_SYSTEM。kernel 層的排程演算法見 CPU Scheduling Algorithms CPU 排程演算法，多核心的負載平衡與 processor affinity 在 Multiprocessor and Real-Time Scheduling 多處理器與即時排程（籌備中）。

看程式碼：多執行緒模型的模擬（排程與 blocking call）
schedule()、blockingCall()、ioDone()
int numKernel(void) {
  if (model == MANY_TO_ONE) return 1;
  if (model == ONE_TO_ONE) return nUser;
  if (model == MANY_TO_MANY) return nLWP;
  return 1 + nLWP;             /* two-level：T0 綁定 K0，其餘共用 nLWP 個 */
}

/* user thread t 能不能用 kernel thread k */
int allowed(int t, int k) {
  if (model == MANY_TO_ONE) return k == 0;
  if (model == ONE_TO_ONE) return k == t;
  if (model == MANY_TO_MANY) return 1;
  return t == 0 ? k == 0 : k >= 1;   /* two-level：bound thread 只用自己的 K0 */
}

/* 排程一輪：kernel 把沒被卡住的 kernel thread 排上 CPU，
   thread library 替每個 kernel thread 挑一個 ready 的 user thread */
int schedule(int running[]) {
  int taken[MAXT] = {0}, cnt = 0;
  for (int k = 0; k < numKernel() && cnt < cores; k++) {
    if (kblocked[k]) continue;                 /* 卡在 system call 的 kernel thread 不能上 CPU */
    for (int t = 0; t < nUser; t++)
      if (!blocked[t] && !taken[t] && allowed(t, k)) {
        taken[t] = 1;
        running[cnt++] = t;
        break;
      }
  }
  return cnt;                                  /* 同時在跑的 user thread 數 */
}

/* user thread t（目前跑在 kernel thread k 上）呼叫 read() 之類的 blocking system call */
void blockingCall(int t, int k) {
  blocked[t] = 1;
  kblocked[k] = 1;             /* kernel 只看得到 kernel thread：卡住的是 k */
  lwpOf[t] = k;
}

/* I/O 完成：t 和它的 kernel thread 回到 ready */
void ioDone(int t) {
  blocked[t] = 0;
  kblocked[lwpOf[t]] = 0;
}

這段模擬把規則寫成程式：schedule() 跳過被卡住的 kernel thread，替其餘的挑一個 ready 的 user thread，最多排滿 cores 顆。同時在跑的數量 = min(CPU 數, 沒被卡住的 kernel thread 數, ready 的 user thread 數)。下面的動畫就是照這套規則畫的。

動手操作

先按上排四個按鈕選模型；輸入框依序是 user thread 數（1～6）、LWP 數（只用在 many-to-many 和 two-level）、CPU 數（1～4），以及依序做 blocking system call 的 thread 編號（例如 0 1，最多 3 個），改完按「執行」。只有正在 CPU 上的 thread 才能發出 system call，輸入沒在跑的 thread 時動畫會停下來說明原因。三個例子分別示範：many-to-one 一個卡住全部卡住、many-to-many 的 LWP 被用完、單核心的 one-to-one（有 concurrency 沒有 parallelism）。

Pthreads 程式：建立、等待與共享

Pthreads（POSIX threads）是 POSIX 定義的 thread API（一份規格，不是某個實作），UNIX 類系統都有。最常用的三個函式：

函式作用
pthread_create(&tid, attr, func, arg)建立 thread，從 func(arg) 開始執行；呼叫者不會等它
pthread_join(tid, &ret)等指定的 thread 結束，並取回它的回傳值
pthread_exit(ret)結束自己這個 thread（只結束 thread，不是整個行程）

parent 建立 child 之後，若會等 child 結束才繼續（例如呼叫 pthread_join），叫 Synchronous Threading（同步執行緒），常見於 parent 要彙整各 child 結果的情況；parent 建完就各跑各的，叫 Asynchronous Threading（非同步執行緒），例如伺服器每個連線一個 thread。編譯時要加 -pthread。

程式輸出題：thread 共享、fork 複製

考題常把 fork() 和 pthread_create() 放在一起，問某個變數最後印出多少。關鍵只有一句：thread 共用同一份 global 變數；fork 出來的 child 拿到的是複本，之後兩邊各改各的。

看程式碼：threadVsFork()
threadVsFork()：thread 改得到、child 改不到
int value = 5;                 /* global 變數 */

void *addTen(void *arg) {
  (void)arg;
  value += 10;                 /* 改到的是同一個 process 裡唯一的那份 value */
  return NULL;
}

void threadVsFork(void) {
  pthread_t t;
  pthread_create(&t, NULL, addTen, NULL);
  pthread_join(t, NULL);
  printf("thread 之後：value = %d\n", value);   /* 15：thread 改的 parent 看得到 */

  fflush(stdout);              /* 先清空緩衝區，避免 fork 後子行程重複印出 */
  pid_t pid = fork();
  if (pid == 0) {              /* 子行程：拿到 value 的一份複本 */
    value += 10;
    printf("child：value = %d\n", value);        /* 25 */
    exit(0);
  }
  waitpid(pid, NULL, 0);
  printf("fork 之後 parent：value = %d\n", value); /* 仍是 15：child 改的是自己的複本 */
}

程式在 fork 前先 fflush(stdout)：printf 的緩衝區也在記憶體裡，若還沒送出就 fork，child 會複製一份沒送出的內容，同一行就印了兩次，這是 fork 輸出題的另一個陷阱。計算 fork 會產生幾個行程的題型（迴圈裡 fork、fork() && fork()）屬於 Process Concept 行程與行程狀態（籌備中）。

共享變數與 race condition

兩個 thread 各對同一個 global 計數器加 10000 次，結果不一定是 20000。count += 1 在機器層級是「讀出、加一、寫回」三步，兩個 thread 可能讀到同一個舊值、各自加一寫回，就少算一次。這種結果取決於執行順序的情況叫 Race Condition（競爭情況）。調整 pthread_join 的順序沒有用（join 只決定 main 先等誰，兩個 thread 照樣同時在跑）；要用 mutex 把「讀、加、寫」包起來：

看程式碼：用 mutex 保護共享計數器
inc()：lock → counter++ → unlock
long counter = 0;
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;

void *inc(void *arg) {
  int times = *(int *)arg;
  for (int i = 0; i < times; i++) {
    pthread_mutex_lock(&lock);
    counter++;                 /* 讀、加、寫三步，鎖住才不會被插隊 */
    pthread_mutex_unlock(&lock);
  }
  return NULL;
}

為什麼需要鎖、鎖要滿足哪些條件，在 The Critical-Section Problem 臨界區問題（籌備中）和 Mutex Locks and Semaphores 互斥鎖與號誌（籌備中）詳細說明。

多執行緒的麻煩：fork、signal、取消

fork() 與 exec()

多執行緒行程裡某個 thread 呼叫 fork()，child 要複製所有 thread，還是只複製呼叫者？有的 UNIX 兩種都提供；POSIX 的 fork() 只複製呼叫 fork 的那個 thread。如果 child 接著馬上 exec()，整個位址空間都會被新程式取代，複製其他 thread 本來就是浪費。exec() 不會保留原本的記憶體或任何 thread，它載入新程式、從新程式的進入點開始執行。

只複製一個 thread 帶來圖 4 的問題：其他 thread 拿著的鎖，在 child 裡永遠解不開。printf、malloc 這類函式內部都有鎖，剛好被其他 thread 拿著時，child 一呼叫就卡死。所以 POSIX 規定 fork 之後、exec 之前，child 只應該呼叫 async-signal-safe 的函式。

Signal 要送給哪個 thread

Signal（信號）是 UNIX 通知行程「發生了某件事」的方式。單執行緒時送給行程就好，多執行緒時要決定由誰處理：

  • Synchronous signal（同步信號）：由某個 thread 自己的動作造成，例如非法存取記憶體（SIGSEGV）、除以 0，送給造成它的那個 thread。
  • Asynchronous signal（非同步信號）：由外部事件造成，例如 kill、Ctrl-C。可以送給所有 thread、送給某些 thread，或指定一個專門接收 signal 的 thread。POSIX 的做法是：送給行程的 signal 交給任一個沒有 block 這個 signal 的 thread；每個 thread 可以用 pthread_sigmask() 決定要 block 哪些 signal，pthread_kill() 則可以把 signal 送給指定的 thread。

Thread Cancellation：提早結束某個 thread

例如多個 thread 同時搜尋資料庫，一個找到後其他都該停。要被取消的 thread 叫 target thread，有兩種取消方式：

  • Asynchronous Cancellation（非同步取消）：立刻終止 target thread。它可能正在更新共享資料或拿著鎖，資源來不及釋放，很危險。
  • Deferred Cancellation（延遲取消）：只設一個「請你結束」的旗標，target thread 執行到 cancellation point（例如 pthread_testcancel()、read() 等許多會 block 的呼叫）時才檢查、結束，可以在安全的地方收尾。Pthreads 的預設是 deferred。
看程式碼：deferred cancellation
spin()：只在 pthread_testcancel() 被取消
volatile int started = 0;

void *spin(void *arg) {
  (void)arg;
  started = 1;
  for (;;) {
    /* ……做一小段不能被打斷的工作…… */
    pthread_testcancel();      /* cancellation point：有取消要求就在這裡結束 */
  }
  return NULL;
}

  pthread_create(&s, NULL, spin, NULL);
  while (!started) sched_yield();   /* 等 spin 真的開始跑 */
  pthread_cancel(s);           /* 只是送出取消要求 */
  pthread_join(s, &res);
  printf("spin %s\n", res == PTHREAD_CANCELED ? "在 cancellation point 被取消" : "正常結束");

pthread_cancel() 只是送出取消要求，真正結束的時間點由 target thread 決定；join 回來的值是 PTHREAD_CANCELED，代表它是被取消的。

Thread-Local Storage

有時每個 thread 需要一份「自己的 global 變數」，例如每個 thread 處理的交易編號。區域變數只在一個函式裡看得到，函式返回就沒了；Thread-Local Storage（執行緒區域儲存，TLS）則在這個 thread 的所有函式裡都看得到、存在到 thread 結束，但每個 thread 各一份（C11 寫成 _Thread_local，gcc 有 __thread）。

隱式執行緒與 Thread Pool

手動建立、管理成百上千個 thread 很容易出錯。現在的趨勢是 Implicit Threading（隱式執行緒）：程式設計者只標出「哪些工作可以平行」，建立與管理 thread 的事交給編譯器和執行期函式庫。

做法概念
Thread pool（執行緒池）啟動時先建好固定數量的 thread 在池子裡等；有工作就交給閒置的 thread，做完回到池子，沒有閒置的就排隊
Fork-joinparent 把工作切成子工作（fork），等它們做完再合併（join）；Java 的 ForkJoinPool 就是這樣
OpenMP在 C/C++ 程式裡用 #pragma omp parallel 這類編譯指示標出平行區域，由編譯器產生 thread
Grand Central Dispatch（GCD）macOS／iOS 的技術：程式把工作（block）放進 dispatch queue，由系統管理的 thread pool 取出執行，程式本身不直接建立 thread
Intel TBBC++ 函式庫，提供 parallel_for 等平行樣板

thread pool 的三個好處：(1) 用現成的 thread 比臨時建立快；(2) 限制同時存在的 thread 數，request 暴增時不會把系統資源耗光，對資源有限的系統特別重要；(3) 把「要做什麼」和「怎麼執行」分開，可以換排程策略（例如延遲執行、定期執行）。pool 的大小可以依 CPU 數、記憶體大小、預期的同時連線數決定，也可以動態調整。

設計題常要你說明伺服器怎麼用 thread：常見答案是 CPU 密集的工作用約等於核心數的 thread（多了只增加切換），I/O 密集的工作則需要更多 thread 或改用非同步 I/O，讓等待 I/O 的時間有別的 thread 補上；共享資料用鎖或分區避免 race condition。
