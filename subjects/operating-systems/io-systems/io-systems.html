I/O 為什麼要特別處理

電腦的工作不外乎兩件事：計算與 I/O。CPU 和記憶體只有少數幾種，I/O 裝置卻千奇百怪：鍵盤、滑鼠、磁碟、SSD、網卡、螢幕、感測器……它們的速度差了好幾個數量級，傳資料的單位也不一樣（一個字元、一個封包、一個 block）。作業系統的 I/O 子系統要解決兩個問題：怎麼用同一套方式控制這麼多不同的裝置，以及怎麼不讓慢吞吞的裝置拖住飛快的 CPU。

裝置傳輸率（數量級）意義
鍵盤約 10 B/s1 GHz 的 CPU 在兩次按鍵之間可以執行上億條指令
滑鼠約 100 B/s每秒幾十到上百次回報，每次幾個 byte
硬碟（HDD）約 100 MB/s比鍵盤快 107 倍，CPU 若一個 byte 一個 byte 搬就會被佔滿
NVMe SSD、10 Gbps 網卡約 1 GB/s 以上每秒上百萬次傳輸，一定要靠 DMA

I/O 硬體：port、bus、controller

裝置透過連接點 Port（埠） 接到電腦，多個裝置共用的一組線路與通訊協定叫 Bus（匯流排），現在 PC 上最主要的是 PCIe。真正和 CPU 打交道的不是裝置本身，而是 Device Controller（裝置控制器）：一塊負責操作 port、bus 或裝置的電子電路（例如磁碟控制器、USB 控制器、網卡上的晶片），複雜的控制器本身就有一顆小處理器和韌體。

controller 通常有四種暫存器，driver 就是靠讀寫它們完成所有 I/O：

暫存器方向用途
data-in裝置 → 主機主機讀它取得輸入資料
data-out主機 → 裝置主機寫它送出輸出資料
status裝置 → 主機忙碌（busy）、資料已備妥（ready）、發生錯誤等狀態位元
control主機 → 裝置下命令（讀、寫）、切換模式（例如全雙工、同位檢查）

每一種裝置的暫存器用法都不同，把這些細節包起來的軟體是 Device Driver（裝置驅動程式），它是 kernel 的一部分，對上層提供統一的介面（讀一個 block、送一個封包），對下讀寫 controller 的暫存器。下面這份模擬的 controller 會用在整頁的程式碼與動畫裡：

看程式碼：模擬的 device controller
Controller、issueRead()、deviceTick()
enum { IDLE, BUSY, READY };
#define CMD_READ 1

typedef struct {
  int status;        /* status register：IDLE／BUSY／READY */
  int control;       /* control register：driver 寫入命令 */
  int dataIn;        /* data-in register：裝置要給主機的資料 */
  int delay;         /* 模擬用：還要幾個時間單位資料才準備好 */
  int next;          /* 模擬用：裝置下一筆資料的值 */
} Controller;

Controller dev;
int ioDelay = 3;     /* 裝置每準備一筆資料要幾個時間單位 */

void issueRead(Controller *c, int delay) {   /* driver 寫 control register 下命令 */
  c->control = CMD_READ;
  c->status = BUSY;
  c->delay = delay;
}

/* 時間前進一個單位；資料剛準備好時回傳 1 */
int deviceTick(Controller *c) {
  if (c->status != BUSY) return 0;
  if (--c->delay > 0) return 0;
  c->dataIn = c->next++;
  c->status = READY;
  return 1;
}

issueRead() 就是 driver 寫 control register 下命令；deviceTick() 模擬裝置經過一段時間把資料放進 data-in、把 status 改成 READY。實際硬體上這兩件事是平行發生的，CPU 不知道裝置什麼時候會好，這正是接下來 polling 與 interrupt 要解決的問題。

I/O 指令與 Memory-Mapped I/O

CPU 要怎麼「讀寫 controller 的暫存器」？有兩種做法，考題常問兩者的差別：

  • Port-Mapped I/O（I/O 指令／獨立 I/O 位址空間）：裝置暫存器在另一個獨立的 I/O 位址空間，每個暫存器有一個 port 號碼，要用專門的 I/O 指令存取，例如 x86 的 in、out。
  • Memory-Mapped I/O（記憶體映射 I/O，MMIO）：把裝置暫存器放進記憶體的實體位址空間，佔用一段位址，CPU 用一般的 load／store 指令讀寫那段位址，實際上就是在讀寫裝置。
比較Port-mapped I/OMemory-mapped I/O
位址空間獨立的 I/O 空間和記憶體共用，佔掉一段位址
存取指令特殊 I/O 指令（in／out）一般 load／store，任何定址模式都能用
大量資料一次一個 byte／word 慢慢送例如顯示卡把整塊畫面記憶體對映進來，直接寫很快
要注意指令集要多一組 I/O 指令那段位址必須設為 uncached；程式寫錯指標可能誤寫到裝置
常見平台x86（傳統裝置，兩種都有）ARM、RISC-V、MIPS 幾乎全是 MMIO；PCIe 裝置也多用 MMIO

不管哪一種，I/O 都是特權操作：in／out 是特權指令，只能在 kernel mode 執行；MMIO 那段位址也不會對映進使用者行程的位址空間。使用者程式要做 I/O 只能透過 system call 請 kernel 代勞，這樣 kernel 才能檢查權限、避免一個程式亂下命令把磁碟弄壞。user mode／kernel mode 的切換在 Interrupts and Dual-Mode Operation 中斷與雙重模式（籌備中）說明。

Polling：CPU 自己一直問

最直接的做法：CPU 下完命令後，在迴圈裡反覆讀 status register，直到裝置說「好了」，再自己把資料搬走。這叫 Polling（輪詢），迴圈本身叫 Busy-Waiting（忙碌等待）；資料由 CPU 一筆一筆搬的方式統稱 Programmed I/O（PIO，程式控制 I/O）。

  1. driver 寫 control register 下命令，裝置把 status 設成 busy。
  2. CPU 反覆讀 status，只要還是 busy 就再讀一次。
  3. 裝置把資料放進 data-in，status 變成 ready。
  4. CPU 讀到 ready，離開迴圈，從 data-in 讀出資料寫進記憶體，清掉 ready。
  5. 要讀多筆就重複 1～4。
看程式碼：pollingRead()
pollingRead()：busy-wait 等 status，再自己搬資料
/* CPU 自己等、自己搬：回傳花在空轉檢查的次數 */
int pollingRead(Controller *c, int *buf, int n, int delay) {
  int polls = 0;
  for (int i = 0; i < n; i++) {
    issueRead(c, delay);                 /* 1. 寫 control register 下命令 */
    while (c->status != READY) {         /* 2. busy-wait：反覆讀 status register */
      polls++;
      deviceTick(c);
    }
    buf[i] = c->dataIn;                  /* 3. CPU 讀 data-in，自己寫進記憶體 */
    c->status = IDLE;                    /* 4. 清掉 ready，準備下一筆 */
  }
  return polls;
}

polling 的成本在哪裡

單看一次 polling 很便宜：讀 status、測一個 bit、條件分支，幾條指令就結束。真正的浪費是一直查、卻很少碰到裝置準備好：裝置越慢，每筆資料要空轉的次數越多，CPU 在這段時間什麼別的事都做不了。上面的程式回傳 polls，就是花在空轉的檢查次數；每筆要等 d 個時間單位，讀 n 筆就空轉 n × d 次。

另一種常見的寫法是週期性 polling：不是死盯著，而是每隔 T 查一次，中間 CPU 可以做別的事。這時要算的是延遲：事件在兩次檢查之間任何時刻發生的機會相同，平均要等 T/2 才被發現，最壞等 T。把 T 縮短能降低延遲，但每秒檢查次數變多，CPU 使用率與耗電一起上升，這是一個取捨，不能兩全。

polling 不一定是壞的：裝置很快（查一兩次就好）、或事件非常頻繁時，polling 省掉了中斷進出的成本，反而更有效率。慢速而且偶爾才有資料的裝置，才是 polling 最浪費的情況。

Interrupt：裝置好了再通知

與其讓 CPU 一直問，不如讓裝置準備好時主動通知 CPU。CPU 有一條 Interrupt-Request Line（中斷請求線），controller 有事時就把它拉起來；CPU 每執行完一條指令就檢查這條線，發現有中斷就暫停目前的程式，跳去執行對應的 Interrupt Service Routine（中斷服務常式，ISR／interrupt handler）。這叫 Interrupt-Driven I/O（中斷驅動 I/O）：下完命令 CPU 就去做別的事，不必盯著 status。

  1. controller 把資料準備好，拉起 interrupt-request line。
  2. CPU 先把正在執行的指令做完，在指令邊界才檢查中斷。
  3. 硬體自動保存 PC 和狀態暫存器（放到 kernel stack），切換到 kernel mode。
  4. 用中斷編號當索引，查 Interrupt Vector Table（中斷向量表），取得 ISR 的位址並跳過去。有了向量表，CPU 不必一個一個問「是哪個裝置發的」。
  5. ISR 處理裝置：讀 data-in、把資料存好、清掉中斷原因，必要時下一筆命令。
  6. 執行「從中斷返回」的指令，恢復狀態，被中斷的程式從原處繼續，完全不知道剛才被打斷過。
看程式碼：向量表、devISR()、CPU 主迴圈
vector[]、devISR()、cpuRun()
typedef void (*Handler)(void);
#define NVEC 8
#define IRQ_DEV 3
#define IRQ_DMA 5
Handler vector[NVEC];                    /* interrupt vector table：中斷編號 → 處理常式 */
int irqLine = -1;                        /* interrupt-request line：-1 表示沒有中斷 */
int useDMA = 0;                          /* 裝置的資料交給 DMA 還是發中斷給 CPU */
int *ioBuf, ioWant, ioPos, ioDone;
int otherWork, interrupts;               /* 等 I/O 時 CPU 做的其他工作、中斷次數 */
int dmaCycle(void);

void devISR(void) {                      /* 裝置的 interrupt service routine */
  ioBuf[ioPos++] = dev.dataIn;           /* 一次中斷搬一筆 */
  dev.status = IDLE;                     /* 回應裝置，清掉中斷原因 */
  if (ioPos < ioWant) issueRead(&dev, ioDelay);   /* 還沒讀完：下一筆的命令 */
  else ioDone = 1;                       /* 讀完：喚醒等待的 process */
}

void cpuRun(void) {                      /* CPU 的主迴圈（模擬） */
  while (!ioDone) {
    otherWork++;                         /* 執行其他 process 的一條指令 */
    if (deviceTick(&dev) && !useDMA) irqLine = IRQ_DEV;
    if (useDMA && dmaCycle()) irqLine = IRQ_DMA;
    if (irqLine >= 0) {                  /* 每條指令結束時檢查 interrupt-request line */
      int irq = irqLine;
      irqLine = -1;
      interrupts++;                      /* 硬體：保存 PC 與狀態、切到 kernel mode */
      vector[irq]();                     /* 查向量表，跳到對應的 handler */
    }                                    /* handler 返回：恢復狀態，回到被中斷的程式 */
  }
}

cpuRun() 模擬 CPU：每執行一條其他程式的指令（otherWork++）就檢查一次 irqLine，有中斷就查 vector[irq] 呼叫對應的 handler。devISR() 一次中斷只搬一筆，所以讀 n 筆就會中斷 n 次，資料仍然是 CPU 搬的：interrupt 改善的是「怎麼知道裝置好了」，不是「誰搬資料」。（程式中 dmaCycle() 的宣告是給後面的 DMA 用的。）

現代中斷機制的細節

  • Maskable 與 nonmaskable：CPU 通常有兩條中斷線。Nonmaskable Interrupt（不可遮罩中斷，NMI）留給記憶體錯誤這類無法恢復的緊急事件；一般裝置用 maskable 中斷，kernel 執行不能被打斷的關鍵程式時可以暫時遮罩（例如 x86 清掉 IF 旗標）。注意遮罩只對外部的 maskable 中斷有效，除以零、page fault 這類 CPU 內部的例外遮不掉。
  • 優先權：中斷分等級，高優先權的可以打斷正在執行的低優先權 ISR，低優先權的則被延後處理。
  • Interrupt chaining：裝置比向量表的項目多時，一個項目指向一串 handler，依序呼叫，直到有一個認領這次中斷。
  • Edge-triggered 與 level-triggered：前者在訊號變化的瞬間觸發，後者在訊號維持時持續觸發。兩者都可能因為高頻或彈跳的訊號造成大量中斷，仍需要 debouncing 或節流。
  • 不只裝置會用：除以零、page fault 等 Exception（例外），以及 system call 用的 Trap（陷阱，軟體中斷），也都在向量表裡有自己的項目，走同一套「保存狀態 → 查表 → 執行 handler」的流程。差別是 trap 和例外由某條指令引起（同步），硬體中斷和目前執行的指令無關（非同步）。CPU 架構層級的例外處理在 Exceptions 例外處理（籌備中）。
  • 誰會發中斷：有主動行為的裝置控制器、計時器、DMA controller、其他 CPU 核心。DRAM 是被動元件，只會被讀寫，不會發中斷。

Top half 與 bottom half

ISR 執行時通常遮罩了同等級的中斷，跑太久會讓其他裝置的中斷等不到。所以中斷處理分成兩半：top half（ISR 本身）只做最急的事，例如回應裝置、把硬體暫存器裡的資料抓下來、排程後續工作；bottom half（Linux 的 softirq、tasklet、work queue）稍後在中斷開啟的情況下做比較花時間的處理，例如解析資料、放進佇列、喚醒等待的行程。以滑鼠為例：ISR 收下原始的位移封包，driver 的 bottom half 把它轉成移動事件放進事件佇列，再喚醒阻塞在 read() 或 select() 上的視窗系統，視窗系統讀到事件才重畫游標。

計時器也是靠中斷運作的：Round Robin 排程每個時間片結束時，就是硬體 timer 發中斷，ISR 呼叫排程器切換行程（見 CPU Scheduling Algorithms CPU 排程演算法）。

DMA：把搬資料交給專門的控制器

interrupt 解決了「等」的浪費，但每筆資料仍要中斷一次、由 CPU 搬一次。磁碟一次要讀幾十 KB、網卡每秒收上百萬個封包，若每幾個 byte 就中斷一次，CPU 光是進出中斷就忙不過來。解法是 Direct Memory Access（直接記憶體存取，DMA）：由一個專門的 DMA controller 在裝置和記憶體之間直接搬資料，CPU 只負責開頭的設定和結尾的一次中斷。

  1. driver 在記憶體準備好 buffer，把來源／目的位址、長度、方向寫進 DMA controller 的暫存器（或寫一個 command block 放在記憶體，把它的位址告訴 DMA），然後對裝置下命令。CPU 接著去做別的事。
  2. 裝置準備好一筆資料，對 DMA controller 送 DMA-request。
  3. DMA controller 取得記憶體匯流排的使用權，送 DMA-acknowledge 給裝置。
  4. 資料直接寫進記憶體，DMA 把目的位址加一、剩餘筆數減一。
  5. 重複 2～4，直到剩餘筆數變成 0。
  6. 整塊搬完，DMA controller 發一次中斷通知 CPU。
看程式碼：dmaStart()、dmaCycle()、dmaISR()
DMA controller 的模擬
typedef struct {
  int *dst;          /* 目的記憶體位址 */
  int count;         /* 還剩幾筆 */
  int busy;
} DMAController;
DMAController dma;
int stolen;          /* DMA 用掉的 bus cycle 數（cycle stealing） */

void dmaISR(void) { ioDone = 1; }        /* 整塊只中斷這一次 */

void dmaStart(int *dst, int n) {         /* driver 寫 DMA 的位址、長度暫存器 */
  dma.dst = dst;
  dma.count = n;
  dma.busy = 1;
  issueRead(&dev, ioDelay);              /* 之後 CPU 就不管了 */
}

/* 裝置有資料（DMA-request）時，DMA 搶一個 bus cycle 寫進記憶體；整塊搬完回傳 1 */
int dmaCycle(void) {
  if (!dma.busy || dev.status != READY) return 0;
  *dma.dst++ = dev.dataIn;               /* 直接寫記憶體，不經過 CPU */
  stolen++;                              /* 這個 bus cycle CPU 用不到 */
  dev.status = IDLE;                     /* DMA-acknowledge：裝置準備下一筆 */
  if (--dma.count > 0) { issueRead(&dev, ioDelay); return 0; }
  dma.busy = 0;
  return 1;                              /* 整塊搬完：發中斷 */
}

和 interrupt 版比較：同樣讀 n 筆，interrupt 版中斷 n 次、CPU 搬 n 筆；DMA 版中斷 1 次、CPU 搬 0 筆。完成通知也不一定要用中斷，CPU 也可以 polling DMA controller 的狀態暫存器，只是通常用中斷。

Cycle stealing 與 burst mode

DMA 搬資料要用記憶體匯流排，這段時間 CPU 不能用匯流排存取記憶體（cache 裡命中的存取不受影響）。DMA 每搬一筆就搶走一個 bus cycle、再還給 CPU，叫 Cycle Stealing（週期竊取）；一次佔住匯流排把整塊連續傳完，叫 Burst Mode（突發模式），傳輸效率較高，但這段時間 CPU 要存取記憶體就得整段等。兩者佔用匯流排的總時間一樣（要搬的資料量一樣），差別只在集中還是分散。所以 DMA 會稍微拖慢 CPU 的計算，但 CPU 不必親手搬資料、不必每筆中斷，整體系統效能仍然提升。

考題愛問的延伸

  • Scatter-gather：DMA 可以接受一串（位址, 長度），一次命令搬多段不連續的記憶體，例如一個封包的 header 和 payload 在不同地方。
  • 小資料用 PIO：DMA 有固定的設定成本（寫暫存器、完成中斷）。只有幾個 byte、又要求低延遲時，CPU 直接搬反而最快完成；DMA 適合大量資料、追求 throughput 的情況。
  • Cache 一致性：DMA 直接讀寫記憶體，不經過 CPU 的 cache。硬體若不會自動維持一致（non-coherent），driver 要自己處理：輸出前把 buffer 的 dirty cache line 寫回（clean），輸入完成後、CPU 讀之前把 buffer 的 cache line invalidate，否則會讀到 cache 裡的舊資料。write-back cache 的運作見 Cache Organization and Mapping 快取組織與映射。
  • 位址與分頁：DMA controller 傳統上用實體位址，不懂行程的頁表。所以 DMA 用的 buffer 必須先 pin 在記憶體裡（傳輸中不能被換出）。IOMMU（I/O 記憶體管理單元）替裝置做位址轉換，讓 DMA 可以用裝置自己的虛擬位址，同時限制裝置只能存取被允許的記憶體。頁表與位址轉換見 Paging and TLB 分頁與 TLB。
  • DMA 不是「讓應用程式直接存取記憶體」：「direct」指的是裝置不經過 CPU 直接和記憶體交換資料。GPU 從主記憶體讀資料、網卡把封包寫進記憶體，都是 DMA。kernel 與 user 之間的資料複製則是記憶體到記憶體，一般由 CPU 做並檢查使用者位址。

動手操作：一次傳輸的訊號流程

用上方三個按鈕選 Polling、Interrupt 或 DMA；兩個輸入框分別是要讀幾筆（1～6）和裝置每筆要準備幾個時間單位（1～5），改完按「執行」。畫面上看得到 CPU、中斷向量表、device controller 的三個暫存器、DMA controller 與記憶體裡的 buf，箭頭是這一步送出的訊號。第一筆會完整走一遍每個步驟，之後的每筆濃縮成一步。頂端的計數器記錄空轉檢查次數、CPU 做了多少其他工作、中斷次數、DMA 偷走的 bus cycle：同樣的筆數與準備時間，切換三種方式比較這幾個數字。

CPU 負擔怎麼算

計組與作業系統都會考「某裝置用 polling／interrupt／DMA 各要花多少 CPU 時間」。解法都一樣：算出每秒發生幾次「要 CPU 處理的事」，乘上每次的週期數，再除以 CPU 每秒的週期數（時脈）。

CPU 時間佔比 = 每秒事件次數 × 每次的週期數 ÷ 時脈

polling   ：事件次數 = 傳輸率 ÷ 每次傳輸量              （裝置閒著也要照查）
interrupt ：事件次數 = 傳輸率 ÷ 每次傳輸量 × 活躍比例
DMA       ：事件次數 = 傳輸率 ÷ 每塊大小 × 活躍比例       （每次 = 設定 + 完成中斷）

polling 那一行不乘活躍比例：CPU 不知道裝置什麼時候會有資料，為了不漏資料只能一直照最高速率查。interrupt 和 DMA 只在真的有資料時才花 CPU。

例：8 MB/s 的硬碟

條件：CPU 1 GHz；每次 poll／中斷搬 16 byte；一次 poll 300 週期、一次中斷 600 週期；DMA 每塊 8 KB（這裡 1 KB = 1000 byte、1 MB = 106 byte，題目若用 1024 要照題目），每塊設定加完成中斷共 3000 週期。

方式每秒事件次數每秒週期數CPU 佔比意義
Polling8×106 / 16 = 5×105× 300 = 1.5×10815%每 7 個週期就有 1 個在查 status
Interrupt（一直在傳）5×105× 600 = 3×10830%比 polling 還高：一次中斷比一次 poll 貴，而裝置沒有閒著的時候
Interrupt（20% 時間在傳）1056×1076%只有 polling 的 40%：閒著的時間不花 CPU
DMA8×106 / 8000 = 1000× 3000 = 3×1060.3%是 polling 的 1/50，中斷次數少了 500 倍

同樣用 polling，每秒只需檢查 30 次的滑鼠（120 B/s、每次 4 byte）只佔 30 × 300 / 109 = 0.0009%，完全可以忽略。這張表說明了三件事：慢速裝置用 polling 就夠了；interrupt 不一定比 polling 省，要看裝置多常在傳；高速裝置一定要用 DMA。

看程式碼：三種方式的 CPU 佔比
pollingLoad()、interruptLoad()、dmaLoad()
/* rate：裝置傳輸率（byte/s）　unit：每次 poll／中斷搬的 byte 數
   clock：CPU 時脈（Hz）　active：裝置真的在傳資料的時間比例（0～1） */
double pollingLoad(double rate, double unit, double cPoll, double clock) {
  double polls = rate / unit;              /* 要跟上裝置，每秒至少查這麼多次 */
  return polls * cPoll / clock;            /* 裝置閒著也得照查，和 active 無關 */
}

double interruptLoad(double rate, double unit, double cInt, double clock, double active) {
  double ints = rate / unit * active;      /* 只有裝置真的在傳時才會中斷 */
  return ints * cInt / clock;
}

double dmaLoad(double rate, double block, double cDma, double clock, double active) {
  double blocks = rate / block * active;   /* 每搬完一整塊才中斷一次 */
  return blocks * cDma / clock;            /* cDma = 設定 DMA + 完成中斷的週期數 */
}

下面的計算器照這三個函式一步一步算，最後畫成長條比較。輸入框依序是：裝置速率（byte/s）、每次傳輸大小（byte）、CPU 時脈（Hz）、一次 poll 的週期、一次中斷的週期、DMA 塊大小（byte）、DMA 每塊的週期（設定＋完成中斷）、裝置活躍 %；數字可以用 K、M、G 代表 103、106、109，例如 8M、1G。超過 100% 的組合會標成紅色，表示 CPU 根本處理不完。

應用程式看到的 I/O 介面

應用程式不會直接面對 controller 的暫存器。kernel 把裝置分成幾大類，每類提供一組標準的 system call，driver 負責把它們翻譯成具體的硬體操作；新裝置只要寫一個符合介面的 driver，應用程式不必改。

類別存取方式例子
Block device（區塊裝置）以 block 為單位 read、write、seek，可以隨機存取；也可以 mmap 對映進記憶體磁碟、SSD
Character device（字元裝置）一個字元一個字元依序 get、put鍵盤、滑鼠、序列埠
Network device（網路裝置）socket 介面：建立連線、send、receive，用 select／poll 等多個 socket網卡
Clock and timer（時鐘與計時器）讀目前時間、設定多久之後觸發programmable interval timer

不屬於標準操作的功能，UNIX 用 ioctl() 這個「萬用」system call，讓應用程式把任意命令傳給 driver。

Blocking、nonblocking 與 asynchronous

  • Blocking I/O（阻塞式 I/O）：呼叫後 process 從 running 移到 waiting，I/O 完成才回到 ready，拿到結果才繼續。程式是直線流程，最容易寫、最容易懂，大部分 system call 預設都是 blocking。
  • Nonblocking I/O（非阻塞式 I/O）：呼叫立刻返回，帶回當下能拿到的資料（可能是 0 byte，或回傳 EAGAIN 之類的錯誤碼），process 不會進入 waiting。適合一邊等輸入、一邊還要更新畫面的程式；常和 select()／poll() 搭配：先阻塞等待任一個 fd 就緒，再對就緒的 fd 做不會卡住的讀寫。
  • Asynchronous I/O（非同步 I/O）：呼叫立刻返回，但 I/O 整個交給 kernel 在背景完成，完成後再用 signal、callback 或完成事件通知（例如 POSIX aio、Linux io_uring）。和 nonblocking 的差別：nonblocking 返回時已經給你「現在有的部分」；async 返回時資料還沒到，要等通知才保證全部到齊。

一句話分辨：blocking「做完才回來」；nonblocking「有多少給多少，馬上回來」；asynchronous「馬上回來，做完再通知你」。

多執行緒程式裡，一個 thread 做 blocking I/O 時其他 thread 能不能繼續，取決於執行緒模型：one-to-one 只卡住自己，many-to-one 整個 process 都卡住（見 Threads and Multithreading Models 執行緒與多執行緒模型）。所以 blocking 的程式寫法加上多執行緒，也能達到「等 I/O 時繼續做別的事」的效果；process 在等待時位於哪個狀態與佇列，見 Process Concept 行程與行程狀態。

另外一個常見的介面是 Vectored I/O（分散／聚集 I/O）：readv()／writev() 一次 system call 就讀寫多個 buffer，省下多次呼叫的成本，概念上和 DMA 的 scatter-gather 對應。

Kernel I/O Subsystem：排程、緩衝、快取、spooling

在 system call 與 driver 之間，kernel 有一層和裝置無關的 Kernel I/O Subsystem（核心 I/O 子系統），提供所有裝置共用的服務。

服務做什麼
I/O scheduling（I/O 排程）重排等待中的請求，提高效率與公平性，例如磁碟依位置排序（見 Disk Scheduling 磁碟排程（籌備中））
Buffering（緩衝）資料在傳輸途中暫放的記憶體區域
Caching（快取）保留資料的副本在較快的記憶體，原本的資料還在別處
Spooling（排存）替一次只能服務一個工作、不能交錯輸出的裝置（印表機）保存各工作的輸出，再依序送出
Device reservation（裝置保留）讓 process 明確地獨占某個裝置，用完再釋放
Error handling（錯誤處理）重試暫時性的錯誤，回傳錯誤碼，記錄錯誤日誌
I/O protection（保護）I/O 指令是特權指令，使用者只能透過 system call，由 kernel 檢查權限

Buffering 的三個理由

  1. 速度不一致：網路一點一點收資料，磁碟一次寫一大塊，中間要有地方累積。
  2. 資料單位不一致：網路封包要先切小再傳、收到後重組，應用程式看到的是一整個訊息。
  3. Copy semantics：應用程式呼叫 write() 後馬上改自己的 buffer，寫出去的應該仍是呼叫當下的內容。kernel 先把資料複製到自己的 buffer，之後怎麼改都不影響。

只有一個 buffer 時，裝置填滿它之後要等 CPU 處理完才能填下一塊，兩邊輪流等對方。Double Buffering（雙緩衝）用兩個 buffer 輪流：CPU 處理 A 的同時，裝置填 B，讓生產者與消費者平行工作。

看程式碼：single buffer 與 double buffering 的總時間
singleBuffer()、doubleBuffer()
/* 裝置填滿一個 buffer 要 tFill，CPU 處理一個 buffer 要 tProc，共 n 個 block */
double singleBuffer(int n, double tFill, double tProc) {
  return n * (tFill + tProc);            /* 只有一個 buffer：裝置和 CPU 輪流等對方 */
}

double doubleBuffer(int n, double tFill, double tProc) {
  double slow = tFill > tProc ? tFill : tProc;
  return tFill + (n - 1) * slow + tProc; /* 兩個 buffer 輪流用：填下一塊與處理這一塊重疊 */
}

例：裝置填一塊 4 ms、CPU 處理一塊 3 ms、共 10 塊。單一 buffer 要 10 × (4 + 3) = 70 ms；double buffering 是 4 + 9 × 4 + 3 = 43 ms，省了約 39%。總時間受較慢的一方限制，所以 double buffering 最多只能把時間壓到接近 n × max(填, 處理)。

Caching 與 buffering 的關係

同一塊記憶體可以同時是 buffer 和 cache：檔案系統的 page cache 把讀過的檔案 block 留在 DRAM，下次讀同一塊直接拿副本（caching）；寫入的資料也先放在這裡，稍後才寫回磁碟（buffering）。DRAM 是揮發性的，斷電就沒了，所以要保證資料真的寫到磁碟，要呼叫 fsync()。

user space 也有一層緩衝：C 的 stdio（printf、puts、fwrite）先把資料存在函式庫的 buffer，滿了（fully buffered）或遇到換行（line buffered，終端機預設）才呼叫一次 write() system call。比較兩種寫法時要分清楚三種時間：user CPU time（函式庫搬資料）、system CPU time（system call 次數與 kernel 的工作）、clock time（含等磁碟）。每次 write 之後都 fsync，等的是磁碟，clock time 大增；line buffering 讓 system call 次數變多，system time 增加。

非同步 I/O 也靠 buffering 實作：kernel 先把資料收進自己的 buffer、讓呼叫立刻返回，背景再慢慢寫到裝置；等不及的應用程式要的是「呼叫不必等裝置」，而 buffer 正好吸收了兩邊的速度差。spooling 則可以看成「替每個工作在磁碟上準備一個大 buffer」。

一次 read() 的完整旅程與效能

把整頁的元件串起來：一個 process 對已開啟的檔案呼叫 blocking read()，大致會經過下面這些步驟。

  1. process 執行 system call（trap），切到 kernel mode。
  2. kernel 檢查參數；若資料已經在 page cache 裡，直接複製到使用者的 buffer 返回，不必碰裝置。
  3. 否則 kernel 把請求交給 driver，process 從 running 移到 waiting，CPU 去排程別的 process。
  4. driver 在 kernel 裡準備 buffer，設定 DMA、對 controller 下命令。
  5. controller 操作裝置，資料由 DMA 寫進 kernel buffer。
  6. 傳完，DMA controller 發中斷；ISR（top half）記錄完成、排程後續處理。
  7. driver 確認結果，通知 kernel I/O subsystem 這個請求完成。
  8. kernel 把資料複製到使用者的 buffer（或放進 page cache 再複製），把 process 移回 ready。
  9. process 被排程執行時，read() 才返回。

I/O 的效能從哪裡省

I/O 是影響系統效能的主因之一：每次 I/O 都要執行 driver、處理中斷、做 context switch、在 kernel 與 user 之間複製資料。改善的方向就是把這些成本減少：

  • 減少 context switch 與中斷：一次處理一批，例如網卡的 interrupt coalescing（累積幾個封包才中斷一次）；流量大時乾脆關掉中斷改用 polling（Linux 網路的 NAPI），因為事件很頻繁時，中斷進出的成本比 polling 還貴。
  • 減少資料複製：用 DMA 讓裝置直接寫記憶體；用 mmap 或 zero-copy（例如 sendfile()）避免 kernel 與 user 之間多複製一次。
  • 把工作往下放：把重複的處理交給 controller 的硬體或韌體（例如網卡算 checksum、SSD 控制器的 FTL 自己做 wear leveling），讓 CPU、匯流排的負擔下降。
  • 平衡 CPU、記憶體、匯流排與 I/O：任何一個成為瓶頸，其他的都會閒著等。

儲存裝置還有自己的效能議題，例如 SSD 的 garbage collection 與 erase 造成少數請求延遲特別長（tail latency）、ECC 能修正的位元數有限、檔案系統與 key-value store 的寫入放大等，這些會在 Disk Scheduling 磁碟排程（籌備中）與 File-System Interface 檔案系統介面與目錄結構（籌備中）討論；題庫裡相關的考古題也標了本主題，可以先看詳解。

易錯點

  • interrupt-driven I/O 要 CPU 不斷檢查 status register → 那是 polling；interrupt 是裝置好了主動通知，CPU 中間可以做別的事 例題
  • polling 沒效率，是因為一次 polling 要執行很多指令 → 一次 polling 只要幾條指令；浪費在反覆查卻很少碰到 ready 例題
  • 用了 interrupt，資料就不用 CPU 搬 → interrupt 只改變「怎麼知道裝置好了」，每筆資料仍由 ISR 搬；不用 CPU 搬的是 DMA 例題
  • DMA 每傳一個 word 中斷一次，或 DMA 完全不用中斷 → 整塊傳完才中斷一次（也可以用 polling 查完成） 例題
  • DMA 讓應用程式可以直接存取主記憶體 → direct 指的是裝置不經 CPU 直接和記憶體交換資料 例題
  • DMA 直接寫記憶體，所以 CPU 讀 buffer 時一定是新資料 → cache 不一致時 CPU 可能讀到舊副本，讀之前要 invalidate；輸出前要 clean 例題
  • DMA 總是比 CPU 搬快，小資料也該用 DMA → DMA 有固定的設定與完成中斷成本；幾個 byte、要求低延遲時 PIO 較好 例題
  • 事件率越高，interrupt 比 polling 越划算 → 事件很頻繁時中斷進出的成本累積起來比 polling 貴（NAPI 在高流量改 polling） 例題
  • 提高 polling 頻率能同時降低延遲與 CPU 使用率 → 延遲降低、CPU 與耗電上升，是取捨；平均延遲 T/2、最壞 T 例題
  • 計算 polling 成本時要乘上裝置的活躍比例 → polling 不知道何時有資料，閒著也要照查；只有 interrupt 和 DMA 乘活躍比例 例題
  • 中斷只能由硬體產生；IF 旗標可以遮掉 page fault → trap（system call）是軟體中斷；IF 只遮罩 maskable 的外部中斷，例外遮不掉 例題
  • DRAM 也會發中斷，CPU 接著切到 kernel 提供服務 → DRAM 是被動元件不發中斷；「切到 kernel 派送服務」描述的是 system call 例題
  • blocking system call 發出後，應用程式繼續執行自己的程式碼 → process 進入 waiting，I/O 完成才繼續；那是 nonblocking／async 的行為 例題
  • asynchronous read 返回時資料已經到齊 → async 返回時 I/O 才開始，要等通知；返回時就給部分資料的是 nonblocking 例題
  • page cache 放在 DRAM，斷電後資料還在 → DRAM 是揮發性的；要確保寫到磁碟得 fsync 例題
  • 印表機輸出先存到磁碟再依序送出，叫 buffering → 給不能交錯輸出的裝置排隊叫 spooling；buffering 是傳輸途中暫放 例題
