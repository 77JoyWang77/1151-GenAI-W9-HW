Paging and TLB 分頁與 TLB把位址切成頁號與位移，用頁表和 TLB 找到實體位置

Ch6 Main Memory 難度 page table TLB EAT multi-level paging inverted page table

為什麼需要分頁

最直覺的記憶體管理是 Contiguous Allocation（連續配置）：每個行程在實體記憶體裡佔一整段連續的空間，用一組 base／limit 暫存器做位址轉換和保護（細節見籌備中的「Contiguous Memory Allocation 連續記憶體配置與碎片」）。它簡單，但有一個治不好的病：行程來來去去之後，空閒空間會被切成很多零碎的洞，這叫 External Fragmentation（外部碎片）。

看圖 1(a)：記憶體裡共有 30 + 20 + 25 = 75 KB 空著，新來的 P4 只要 60 KB，可是沒有任何一個洞大於等於 60 KB，P4 還是放不進去。解法之一是 compaction（把行程往同一邊搬、把洞合併），但搬動要複製大量資料，而且行程必須能在執行期間重新定位，代價很高。

問題的根源在於「一個行程必須連續」。Paging（分頁）換個想法：

  • 把實體記憶體切成固定大小的 Frame（頁框）。
  • 把每個行程的邏輯位址空間切成同樣大小的 Page（頁）。
  • 每一頁可以放進任何一個空的 frame，不必相鄰；用一張 Page Table（頁表）記下「第幾頁放在第幾個 frame」。

行程看到的邏輯位址仍然是 0 開始、連續的一整段；只是背後每一頁散落在不同的 frame。因為所有 frame 一樣大，任何空 frame 都能拿來用，外部碎片就消失了（圖 1(b)）。代價是每次存取記憶體都要多做一次查表，以及最後一頁可能用不滿（內部碎片，下面會算）。

分頁的本質：邏輯上連續、實體上分散。頁表負責把兩者接起來，硬體中負責查表的單元叫 MMU（Memory-Management Unit，記憶體管理單元）。

位址怎麼切、怎麼轉換

邏輯位址 = 頁號 p ＋ 頁內位移 d

頁大小一定是 2 的次方，設為 2n bytes。CPU 產生的邏輯位址（m 位元）就可以直接切成兩段：

  • page number p（高 m − n 位元）：第幾頁，用來當頁表的索引。p = 位址 ÷ 頁大小。
  • page offset d（低 n 位元）：頁內第幾個 byte。d = 位址 mod 頁大小。

轉換時 MMU 用 p 查頁表得到 frame 號 f，d 原封不動，實體位址 = f × 頁大小 + d，也就是把 f 和 d 的位元接在一起。因為頁大小是 2 的次方，除法和 mod 都只是「從中間切開位元」，硬體不用做除法。

p = ⌊位址 / 2^n⌋          d = 位址 mod 2^n
實體位址 = 頁表[p] × 2^n + d

例子：頁 1 KB、16 位元邏輯位址

頁大小 1 KB = 210，offset 10 位元；頁號 16 − 10 = 6 位元，邏輯空間最多 26 = 64 頁。實體記憶體 16 KB，共 16 KB ÷ 1 KB = 16 個 frame，實體位址只要 14 位元，比邏輯位址短：邏輯空間和實體空間的大小互相獨立，頁數和 frame 數通常不一樣。設頁表為 0→7、1→3、2→12、5→9，其餘 invalid：

頁大小是 16 的次方（4 KB = 163）時，十六進位位址可以直接用「看字」的方式切：32 位元、頁 4 KB，offset 12 位元剛好是最後 3 個十六進位數字。例如 0x00402A1C：d = 0xA1C，p = 0x00402。頁大小不是 16 的次方（例如 1 KB）時就要先換成二進位再切，不能只看十六進位字。

每個行程有自己的頁表，頁表放在記憶體裡，起點記在 PTBR（Page-Table Base Register，頁表基底暫存器）；context switch 時只要換掉 PTBR 的值（存在 PCB 裡的是這個指標，不是整張頁表）。同一個行程的多個 thread 共用位址空間，也就共用同一張頁表。

看程式碼：translateBasic() 不用 TLB 的位址轉換
translateBasic()：切 p / d、查頁表
int translateBasic(int addr) {
  int p = addr / pageSize;           /* 頁號 = 位址 ÷ 頁大小 */
  int d = addr % pageSize;           /* offset = 位址 mod 頁大小 */
  if (p >= numPages || !pageTable[p].valid) return -1;   /* 超出範圍或 invalid：trap */
  return pageTable[p].frame * pageSize + d;
}

內部碎片與頁大小的取捨

分頁沒有外部碎片，但有 Internal Fragmentation（內部碎片）：行程大小通常不是頁大小的整數倍，最後一頁用不滿，剩下的空間別人也不能用。例如頁 4 KB、行程 10,300 B，要 ⌈10300 / 4096⌉ = 3 頁（12,288 B），最後一頁浪費 12,288 − 10,300 = 1,988 B。

最壞浪費「一頁少 1 byte」，最好剛好 0；假設行程大小隨機，平均每個行程浪費半頁。所以頁越小，內部碎片越少。那為什麼現代系統的頁反而越來越大？因為頁大小是一連串取捨：

考量頁小一點頁大一點
內部碎片（平均半頁）較少較多
頁表大小（頁數 × PTE）較大較小
TLB 涵蓋範圍（格數 × 頁大小）較小，TLB miss 多較大，TLB miss 少
磁碟 I/O（搭配需求分頁時）每次搬得少，seek 與旋轉延遲分攤不掉一次搬一大塊較划算，但可能載入用不到的資料
page fault 次數同樣的區域性要更多頁，fault 較多較少

CPU 和記憶體容量成長得比磁碟快，所以趨勢是用更大的頁；x86-64 除了 4 KB 還支援 2 MB、1 GB 的 huge page。一個 2 MB 的 huge page 在 TLB 裡只佔 1 格，卻涵蓋 512 個 4 KB 頁的範圍，掃大陣列、大型資料庫、機器學習這種工作量很適合；代價是內部碎片變大，copy-on-write、搬移頁面時一次要處理 2 MB。

TLB：頁表的快取

頁表放在記憶體裡，於是每次存取資料其實要存取記憶體兩次：一次讀頁表拿 frame 號，一次讀資料。記憶體存取時間直接變成兩倍，這是不能接受的。解法是在 MMU 裡放一個小而快的快取，專門存「最近用過的頁號 → frame 號」，叫 TLB（Translation Look-aside Buffer，轉換後備緩衝區）。

運作流程

  1. CPU 送出邏輯位址，切出 p 和 d。
  2. 拿 p 去查 TLB。TLB 是 全關聯的：每一格都存（頁號, frame 號），所有格子同時比對頁號，通常只有 32～1024 格（全關聯的觀念見計算機組織的 Cache Organization and Mapping 快取組織與映射）。
  3. TLB hit：直接拿到 frame 號，接上 d 去讀資料，只多花一次 TLB 時間。
  4. TLB miss：到記憶體讀頁表拿 frame 號，再把這筆對應放進 TLB；TLB 滿了就依替換策略換掉一格，考題沒說明時用 LRU（換掉最久沒用的）。

TLB 存的方向是 頁號 → frame 號（用虛擬頁號當 key 查詢）。所以兩個不同的虛擬頁即使指向同一個 frame，在 TLB 裡也是兩筆不同的 entry。

TLB miss 不等於 page fault

TLB 只是快取，miss 只代表「這筆對應最近沒被用過、沒留在 TLB 裡」，頁通常好好地在記憶體裡，讀頁表就拿得到。只有頁表裡那一格是 invalid 時才會 trap 給作業系統，也就是 page fault（要從磁碟載入頁面，屬於籌備中的「Demand Paging 需求分頁與有效存取時間」）。三者的代價差很多：TLB hit 約 1 ns 等級、TLB miss 多一兩百 ns、page fault 要數毫秒，差了四五個數量級。

TLB miss 由誰處理依架構而定：x86、ARM 是 硬體（MMU 內的 page walker 自己走頁表，作業系統不介入）；MIPS、UltraSPARC 是 軟體（trap 給作業系統，由 OS 查表再填入 TLB）。考題常拿 x86 出題，答案是硬體。

Context switch 與 ASID

每個行程的頁表不同，同一個頁號 5 在 A 行程和 B 行程對到不同 frame。切換行程時，TLB 裡舊行程的 entry 就不能再用，有兩種做法：

  • Flush：切換時把整個 TLB 作廢。簡單，但新行程一開始每次存取都 miss。
  • ASID（Address-Space Identifier，位址空間識別碼）：每一格多存一個 ASID，查詢時頁號和 ASID 都要對上才算命中。不同行程的 entry 可以同時留在 TLB 裡，切換時不必清空。

同一個行程內切換 thread 不換位址空間，PTBR 和 TLB 都不用動。另外作業系統核心常用的轉換可以設成 wired down（鎖定），不會被替換掉。

看程式碼：tlbLookup() / tlbInsert()（全關聯＋LRU）
tlbLookup()：比對每一格的頁號
int tlbLookup(int p) {
  now++;
  for (int i = 0; i < tlbSize; i++)
    if (tlb[i].valid && tlb[i].page == p) {
      tlb[i].lastUsed = now;         /* LRU：記下最後使用時間 */
      return tlb[i].frame;
    }
  return -1;                         /* TLB miss */
}
tlbInsert()：先找空格，再換掉 LRU
void tlbInsert(int p, int f) {
  int v = 0;                         /* 先找空格，沒有空格就換掉最久沒用的 */
  for (int i = 0; i < tlbSize; i++) {
    if (!tlb[i].valid) { v = i; break; }
    if (tlb[i].lastUsed < tlb[v].lastUsed) v = i;
  }
  tlb[v].valid = 1;
  tlb[v].page = p;
  tlb[v].frame = f;
  tlb[v].lastUsed = now;
}
看程式碼：translate() 單層頁表＋TLB
translate()：先查 TLB，失誤再讀頁表
int translate(int addr) {
  int p = addr / pageSize;           /* 頁號：位址的高位元 */
  int d = addr % pageSize;           /* offset：位址的低位元 */
  int f = tlbLookup(p);              /* 先查 TLB */
  if (f >= 0) {
    tlbHits++;
    return f * pageSize + d;         /* TLB 命中：不用讀頁表 */
  }
  tlbMisses++;
  memRefs++;                         /* TLB 失誤：到記憶體讀頁表 */
  if (!pageTable[p].valid) return -1;   /* invalid：trap 給作業系統 */
  f = pageTable[p].frame;
  tlbInsert(p, f);                   /* 放進 TLB，滿了換掉 LRU */
  return f * pageSize + d;           /* 實體位址 = frame 起點 + offset */
}

有效存取時間 EAT

有了 TLB，每次存取的時間取決於有沒有命中。設 TLB 命中率（hit ratio）為 h、查 TLB 要 t、存取一次記憶體要 m，頁表為單層：

  • 命中：查 TLB ＋ 讀資料 = t + m。
  • 失誤：查 TLB ＋ 讀頁表 ＋ 讀資料 = t + 2m。
EAT = h × (t + m) + (1 − h) × (t + 2m)
多層頁表（k 層）：失誤時 = t + k·m + m

例：t = 10 ns、m = 100 ns、h = 98%。EAT = 0.98 × 110 + 0.02 × 210 = 107.8 + 4.2 = 112 ns。和「每次都只要讀一次記憶體」的 100 ns 相比只慢 12%；如果沒有 TLB，每次都要 200 ns，慢 100%。TLB 只有幾十格，就把頁表造成的額外負擔從 100% 壓到 12%，這就是區域性的威力。

命中率 h0%50%80%90%95%99%100%
單層 EAT（ns）210160130120115111110
兩層 EAT（ns）310210150130120112110

表中固定 t = 10、m = 100，只改命中率和層數。看兩件事：命中率越高，層數的影響越小（99% 時兩層只比單層慢 1 ns）；命中率低時多層頁表很傷（0% 時兩層比單層多 100 ns）。所以多層頁表更需要 TLB。

反推命中率

題目也常反過來問「要 EAT 不超過某個值，命中率至少多少」。把 EAT 寫成 h 的一次式再解不等式：t = 20、m = 100、單層、要求 EAT < 140 ns，EAT = 120h + 220(1 − h) = 220 − 100h < 140，得 h > 0.8，命中率要超過 80%。

不同題目的假設

  • 大多數題目（包括這頁）假設先查 TLB，失誤後才讀頁表，所以失誤時 TLB 時間也要算。
  • 有些題目假設 TLB 和頁表平行查詢，或 TLB 時間可忽略，失誤時就是 2m。題目沒給 TLB 時間時，通常就是這種。
  • 題目把 page fault 也算進來時，再加上 page fault 率 × 處理時間（毫秒等級），屬於需求分頁的 EAT（籌備中）。
看程式碼：eat() / minHitRatio()
eat()：TLB 命中與失誤的加權平均
double eat(double hit, double tlbTime, double memTime, int levels) {
  double hitTime = tlbTime + memTime;                       /* 查 TLB + 存取資料 */
  double missTime = tlbTime + levels * memTime + memTime;   /* 再加上走頁表 */
  return hit * hitTime + (1 - hit) * missTime;
}
minHitRatio()：EAT 不超過 target 的最低命中率
double minHitRatio(double target, double tlbTime, double memTime, int levels) {
  double hitTime = tlbTime + memTime;
  double missTime = tlbTime + levels * memTime + memTime;
  return (missTime - target) / (missTime - hitTime);
}

動手操作

輸入一串邏輯位址、頁大小、8 格頁表（「-」表示 invalid）和 TLB 格數，看每個位址怎麼切成 p 和 d、TLB 有沒有命中、失誤時怎麼讀頁表並用 LRU 更新 TLB。最後一步會算出命中率和 EAT（設 TLB 10 ns、記憶體 100 ns）。按「兩層頁表」時，頁號 3 位元再切成 p1（2 位元）和 p2（1 位元），一次 TLB miss 要讀外層、內層各一次。

保護與共享

保護位元與 valid-invalid 位元

每個 PTE（Page-Table Entry，頁表項）除了 frame 號，還有幾個控制位元：

  • protection bits：這一頁可讀、可寫、可執行（r／w／x）。例如程式碼頁設成唯讀，寫入時 MMU 會 trap，避免程式改到自己的指令。檢查和位址轉換同時做，不多花時間。
  • valid-invalid bit：v 表示這一頁屬於行程合法的位址空間（而且在記憶體裡）；i 表示不合法或還不在記憶體，存取時 trap 給作業系統。
  • 行程通常只用到位址空間的一小部分，頁表不一定要做滿整個空間：可以用 PTLR（Page-Table Length Register）記錄頁表長度，頁號超過就直接 trap。

使用者程式只能產生邏輯位址，所有位址都要經過自己的頁表轉換，而頁表只有 kernel 能修改；行程沒辦法碰到不屬於它的 frame，這就是分頁天生的記憶體保護。注意 valid 位元是以頁為單位：行程大小 10,300 B、頁 4 KB 時，第 2 頁的 10,300～12,287 雖然超出程式範圍，但仍屬於 valid 的頁，存取不會 trap，這也是內部碎片的副作用。

共享頁

頁表讓多個行程共享同一塊實體記憶體變得很容易：只要兩張頁表的某一格指向同一個 frame。典型例子是 reentrant code（純程式碼、執行時不會修改自己），例如文字編輯器或 C 函式庫：10 個使用者同時執行，程式碼只需要在記憶體裡放一份，每個人只有自己的資料頁。

幾個容易考的細節：

  • 共享的頁在兩個行程中不必對到同一個虛擬位址，各自的頁表愛放哪就放哪。
  • 保護位元記在各自的 PTE 裡：P1 把共享頁設成唯讀，不影響 P2 那邊能不能寫。
  • 真正共享同一個 frame 時，一邊寫入另一邊馬上看得到。fork 時用的 copy-on-write 一開始也共享，但寫入時才複製一份，屬於需求分頁的內容（籌備中）。
  • 反向頁表（後面介紹）每個 frame 只有一格、只能記一個（pid, 頁號），共享頁比較難做。

頁表太大：多層頁表

單層頁表的問題前面算過：32 位元、頁 4 KB、PTE 4 B 時每個行程 4 MB，而且要一整塊連續的記憶體；64 位元用一樣的參數，頁表要 252 × 4 B，根本放不下。但大部分行程的位址空間很稀疏：程式碼和資料在低位址、stack 在高位址，中間一大片沒用到，單層頁表卻得替每一頁都留一格。

Hierarchical Paging（階層式分頁，又叫多層頁表）的想法是「把頁表也分頁」：頁表本身切成一頁一頁，再用一張外層頁表記錄每一頁頁表放在哪裡。整段沒用到的區域，對應的內層頁表就不配置，外層那一格寫 NULL（invalid）即可。

兩層頁表：32 位元、頁 4 KB、PTE 4 B

  • offset：4 KB = 212，12 位元。
  • 每張頁表剛好放一頁：4 KB ÷ 4 B = 1024 = 210 格，所以每一層吃 10 位元。
  • 頁號 20 位元切成 p1（外層索引）10 位元＋ p2（內層索引）10 位元，位址寫成 10 | 10 | 12。
  • 一張內層表涵蓋 1024 頁 × 4 KB = 4 MB 的位址空間。

省多少？假設行程只用最低 8 MB（程式碼＋資料）和最高 4 MB（stack）：內層表需要 8 / 4 + 4 / 4 = 3 張，加上外層 1 張，共 4 頁 = 16 KB，單層要 4 MB，只用了 0.4%。但如果整個 4 GB 都用滿，兩層要 1024 張內層表＋1 張外層 = 4 MB + 4 KB，反而比單層多一頁：多層頁表省的是稀疏空間，不是任何情況都省。

一般的切法：要幾層

通則是「每一張頁表剛好放進一頁」：

每層位元數 = log2(頁大小 / PTE 大小)
層數 = ⌈(位址位元數 − offset 位元數) / 每層位元數⌉
最上層只用剩下的位元（可能比一頁少）
位址頁大小PTEoffset頁號每層層數最上層
32 位元4 KB4 B122010210 位元
48 位元（x86-64）4 KB8 B1236949 位元
64 位元8 KB8 B13511061 位元

x86-64 那一列就是真實的 4 層頁表（9 | 9 | 9 | 9 | 12）。64 位元那列只是把位元數除一除就要 6 層，這也是 64 位元系統只實際使用 48 或 57 位元位址的原因之一。

代價：一次轉換要幾次記憶體存取

k 層頁表在 TLB miss 時要依序讀 k 張表，加上讀資料共 k + 1 次記憶體存取：兩層 3 次、x86-64 的四層 5 次。所以多層頁表一定要配 TLB（上一節的表：命中率 99% 時兩層只比單層慢 1 ns）。另外 2 MB 的 huge page 在 x86-64 上只要走 3 層，因為最後 21 位元都是 offset。

看程式碼：levelSplit() 算層數與各層位元數
levelSplit()：每張表放一頁時要幾層
void levelSplit(int vaBits, long long pageBytes, int pteBytes) {
  int offset = log2i(pageBytes);
  int perLevel = log2i(pageBytes / pteBytes);   /* 一頁放 2^perLevel 個 entry */
  int vpn = vaBits - offset;                    /* 要被各層頁表吃掉的位元 */
  int levels = (vpn + perLevel - 1) / perLevel; /* 無條件進位 */
  int top = vpn - (levels - 1) * perLevel;      /* 最上層只用剩下的位元 */
  printf("%d 位元位址、頁 %lld B、PTE %d B：offset %d、每層 %d 位元，頁號 %d 位元 → %d 層，最上層 %d 位元；"
         "TLB miss 要讀 %d 次頁表＋1 次資料\n",
         vaBits, pageBytes, pteBytes, offset, perLevel, vpn, levels, top, levels);
}
看程式碼：translate2() 兩層頁表＋TLB
translate2()：外層、內層各讀一次
int translate2(int addr) {
  int p = addr / pageSize, d = addr % pageSize;
  int p1 = p / INNER;                /* 外層索引：頁號的高位元 */
  int p2 = p % INNER;                /* 內層索引：頁號的低位元 */
  int f = tlbLookup(p);              /* TLB 仍然用完整的頁號查 */
  if (f >= 0) {
    tlbHits++;
    return f * pageSize + d;
  }
  tlbMisses++;
  memRefs++;                         /* 第 1 次：讀外層頁表 */
  if (outer[p1] == NULL) return -1;  /* 內層表不存在：trap */
  memRefs++;                         /* 第 2 次：讀內層頁表 */
  if (!outer[p1][p2].valid) return -1;
  f = outer[p1][p2].frame;
  tlbInsert(p, f);
  return f * pageSize + d;
}

雜湊頁表與反向頁表

多層頁表在 64 位元時層數太多，另外兩種結構換個角度解決「頁表太大」：

Hashed Page Table 雜湊頁表

Hashed Page Table（雜湊頁表）把虛擬頁號丟進雜湊函數，得到雜湊表的一格；每格是一條鏈結串列，節點存（虛擬頁號, frame 號, 下一個）。查詢時沿著串列比對頁號，找到就得到 frame。表的大小跟「實際用到的頁數」有關，不必替沒用到的頁留位置，適合大於 32 位元的位址空間。變形 clustered page table 讓每個節點記錄連續好幾頁（例如 16 頁），對稀疏但成群的位址空間更省。缺點是碰撞時要走串列，最壞情況存取次數不固定。

Inverted Page Table 反向頁表

前面的頁表都是「每個行程一張、每個虛擬頁一格」。Inverted Page Table（反向頁表）反過來：全系統只有一張、每個實體 frame 一格，第 i 格記錄「frame i 現在放的是哪個行程（pid）的哪一頁」。表的大小只跟實體記憶體有關：1 GB 實體記憶體、頁 4 KB 有 218 個 frame，每格 8 B，整張表 2 MB；同樣的 100 個行程如果各用 4 MB 的單層頁表，要 400 MB。

代價是查詢方向反了：要找 (pid, p) 在哪個 frame，只能在表裡搜尋（找到的列號就是 frame 號），最壞要比對整張表。實務上用雜湊表加速，並靠 TLB 擋掉大部分查詢。

單層頁表多層頁表雜湊頁表反向頁表
幾張表每行程 1 張每行程 1 棵樹每行程 1 張（或共用）全系統 1 張
格數由什麼決定虛擬頁數實際用到的區段實際用到的頁數實體 frame 數
TLB miss 時查表1 次存取每層 1 次雜湊＋走串列，不固定搜尋（搭配雜湊）
優點最簡單、查一次就好稀疏空間很省適合 64 位元總大小最小、和行程數無關
缺點太大、要連續空間層數多、存取次數多碰撞時變慢查詢慢、共享頁難做

反向頁表只記錄「在記憶體裡的頁」，不在記憶體的頁還是需要另外的資料結構記錄它們在磁碟的位置，這部分和需求分頁一起看（籌備中）。

易錯點

  • TLB miss 就是 page fault → TLB miss 只是這筆對應沒被快取，讀頁表通常就拿得到；頁表裡是 invalid 才是 page fault 例題
  • TLB 存的是 frame 號 → 頁號 → 方向是頁號 → frame 號，用虛擬頁號查詢 例題
  • TLB 失誤時只要 t + m → 失誤要多讀頁表：單層 t + 2m，k 層 t + (k + 1)m 例題
  • 多層頁表在任何情況都比單層省記憶體 → 只在位址空間稀疏時省；全部用滿時多了上層表，反而比較大，而且每次轉換存取次數更多 例題
  • 反向頁表每個虛擬頁一格 → 每個實體 frame 一格、全系統一張，大小只跟實體記憶體有關 例題
  • 頁表的格數和實體記憶體大小有關 → 格數由邏輯位址空間決定；實體大小只影響 frame 數與 PTE 內 frame 欄位長度，算層數時是干擾條件 例題
  • 共享頁在兩個行程中一定是同一個虛擬位址，一邊設唯讀另一邊也不能寫 → 共享的是 frame，各自的頁表可以放在不同虛擬頁、設不同保護位元 例題
  • x86 的 TLB miss 由作業系統走頁表 → x86 由 MMU 硬體走頁表，OS 只處理 page fault 例題
  • 同一個行程內切換 thread 也要換 PTBR、清 TLB → thread 共用位址空間，PTBR 不變；換行程時才要 flush 或靠 ASID 例題
  • 內部碎片最多半頁 → 平均半頁，最壞接近一整頁（行程比整數頁多 1 byte） 例題
